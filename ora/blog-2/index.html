ORA · Open Robot-Use Agents

Open models can drive robots now. The interface decides how well.

In October we released ORA, a harness that lets a language model operate a simulated robot the way a coding agent operates a repository: it reads observations, calls tools, checks what happened and decides what to do next. With one open-weight model and no robot training, it solved 69% of RoboTwin and 81% of LIBERO-Pro.

This release keeps the same idea and the same model family, and rebuilds most of what sits around the model. With self-hosted DeepSeek-V4.1-Flash, zero-shot, ORA now solves:

Benchmark Cases October Now
RoboTwin C2R 235 69.2% 79.6%
LIBERO-Pro (Task + Swap) 400 81.4% 88.0%
LIBERO-Pro (all four perturbations) 800 – 87.5%
RoboLab 500 – 79.2%
RoboDojo 200 – 40.5%

RoboDojo is a long, contact-rich, multi-stage benchmark, and it remains our hardest. Getting an open model with no trained policy underneath to finish 40% of RoboDojo cases is the result we worked hardest for.

Two notes before the details. First, RoboLab and RoboDojo define a simulator step limit, and many of our successes arrive after it; the table counts them, and Appendix A gives the official-only numbers and explains why we report both. Second, the October release has no scored result on those two benchmarks under this protocol, so we measure improvement only on RoboTwin and LIBERO-Pro. There the comparison is clean: same benchmarks and case lists (235 of the 250 RoboTwin cases now, the ones RoboTwin's own expert can solve on our installation). Most of the gain already shows up when the model acts as it did in October, one tool call at a time (80.4% and 85.5%); that arm also runs at a higher reasoning effort than October's, so the gain belongs to the harness and the effort setting together, not to code mode.

What changed falls into three parts, and this post follows them:

  1. A new agent core. ORA's agent loop now runs on Pi, an open coding-agent core.
  2. Code mode. The model can write a short program each turn instead of calling one tool. Same tools, same budgets, very different behavior on long tasks.
  3. Agents and models. We ran other agent systems with the same model on the same tasks, and other open models inside ORA.

1. An agent core borrowed from coding agents

ORA's first version had its own Python agent loop. It worked, but every feature a coding agent has for free (sessions, steering mid-task, a terminal UI, a web view, provider plumbing, context compaction) we had to build again, and usually worse.

So we moved the loop onto Pi, an open, minimal coding-agent core, and drew a hard line through the system:

  • Pi (TypeScript) owns what the model sees and when it is called. The provider loop, request assembly, context management and compaction, the tool-dispatch protocol, sessions, steering and the terminal and web front ends. It knows nothing about robots.
  • ORA (Python) owns the robot. The tools, how robot feedback is projected into text and images, the environment workers, and the Supervisor, which admits every motion, enforces the budgets and is the only path to the benchmark's official verdict. Evaluation, sealing and replay stay on this side too.

We required the move to be invisible to the benchmarks. Before switching the default, we replayed recorded episodes through both cores and compared the model requests byte for byte: 37 of 37 LIBERO-Pro default cases, plus RoboTwin and RoboDojo acceptance runs, were identical. TBD: confirm the final replay-check counts in the release notes.

What the move bought is interaction. Because Pi already knows how to hold a session open and accept a message while it works, ORA gained a free-play mode almost for free: load a scene with no task, type instructions, interrupt.

In this take the model first lifted the blue block off the magenta one, as the first instruction required. The correction arrived while it was working; it read it before its next step, re-measured the magenta block, put blue back on it and green on top, and reported the measured height of each layer (a 105 mm tower, layers within about 2 mm of each other laterally). Ten and a half minutes, seven motions, fifteen model calls. One take, so it shows the behavior, not a success rate.

ora play runs in a terminal or in a browser (ora web), and ora watch follows any live run as a transcript. Play sessions are recorded like benchmark runs but never scored and never used as training data.

2. Code mode: same harness, different freedom

Two ways to use the same tools

ORA gives the model perception tools (segmentation, metric 3D measurement from depth), planning tools (grasp proposals, reachability) and motion tools (Cartesian moves, gripper, wrist). In October the model used them one at a time: call a tool, read the result, call the next. Every motion returned a receipt and a fresh observation before the next decision.

In code mode, the same tools are a Python library inside a sandbox, and each turn the model writes a short program. It is still a turn-based loop. One program is one decision, and the model reads the program's output and the next observation before writing the next one. What a program adds is everything around the tool calls: it can compute on a depth point cloud without copying numbers through its reasoning, branch on what it measures, check reachability before moving and the miss after, and hand control back with a reason when a check fails. Programs also persist: the sandbox keeps a working directory, /work, for the whole episode, so the model can write a helper in one turn and import it in the next.

Nothing else changes. The tools are the same, every motion still passes the Supervisor one at a time, and the budgets are the same: 80 robot decisions, 200 model calls, six hours.

On short tasks: the same success, cheaper

On RoboTwin and LIBERO-Pro, where most tasks take a handful of motions, the two modes solve almost the same cases (RoboTwin 187 vs 189 of 235; LIBERO-Pro 700 vs 683 of 800). Code mode is cheaper: about 40% fewer prompt tokens per success, and the share of episode time spent waiting for the model drops from 71–76% to 38–45%, because one call now carries several actions and their checks.

On long tasks: a different outcome

RoboDojo is where the modes separate. We ran a paired experiment on 20 RoboDojo tasks × 3 layouts, with the same model, budgets and tools, changing only the action mode. Programs solved 20 of 59 cases; tool calls solved 6. Fifteen cases were solved only with programs, one only with tool calls.

The first thing we checked was whether code mode simply thinks more. It does not. Both modes reason about equally long per model call (median 10.8k vs 12.0k characters). The difference is what a turn delivers: 97% of tool-call turns that move the robot execute exactly one motion, while a program executes 3.6 on average, together with the measurements around them. Per robot action, tool calls spend 33.4k characters of reasoning and programs 12.7k.

It is also not that long reasoning turns into more motions. Within code mode, a turn's reasoning length is slightly anti-correlated with its motions (Spearman −0.11); the longest turns produce measurement programs that do not move the robot at all: fitting every hole of a test-tube rack, scanning reachable poses, comparing tile faces. Their results come back as numbers that later turns reuse.

Why tool calls fail

Reading the 15 cases only programs solved, the tool-call runs fail in four recurring ways. Each has a counterpart in the program run of the same case.

Estimates drift between turns. With tool calls, a measured quantity lives only in the model's text and is estimated again next turn. Playing a xylophone, the tool-call run revised its key map three times, estimated the mallet's head offset at least six times and restarted the sequence at least six times before running out of decisions. On another layout it counted the keys as nine, then ten; there are eight. The program run fitted the key boundaries once from the point cloud (largest residual 2.6 mm), stored the measured mallet offset in a file that every later program read, and struck all eight keys in three programs.

Each measurement costs a turn. Every perception or geometry call takes a whole turn, and the tool-call mode's calculator accepts only expressions over literals. Inserting test tubes, the tool-call run probed the rack point by point for more than 20 turns and set a tube between two holes, about 18 mm from the nearest centre. One program, running 0.76 s without moving the robot, segmented the depth image and fitted circles to all ten holes (radii 15.6–15.8 mm).

Outcomes are checked a turn later, if at all. Fastening nuts, the tool-call run declared a nut "fully threaded" three times from the arm's position, released it, and watched it drop. The program measured the nut's depth below the bolt tip from the point cloud after every press and pressed again while it still moved (gains 2.93 mm, then 0.03 mm, then stop). It succeeded within the step limit.

Each action costs a full turn of reasoning. Tool calls spend 1.95 model calls per robot action against 0.75 for programs. On the 15 cases, ten tool-call episodes ended with the model abandoning the task, several with most of the budget left. One stopped "for lack of time" with five hours and 52 decisions remaining.

Is it just a bigger action budget?

A program counts as one decision however many motions it issues, up to 12. On those 15 cases, programs executed 1,079 motions in 239 decisions; tool calls executed 823 in 790. So we reran the tool-call arm on the same 15 cases with 300 decisions, 600 model calls and 12 hours, roughly the motions programs had available.

Tool calls then solved 3 of 15. Only two of those needed more than 80 decisions; the third succeeded in 27 and reflects run-to-run variance. None of the twelve failures reached the new cap: nine ended with the model abandoning the task after 35 to 166 decisions, three in the benchmark's failure latch. The model's own reasons for stopping show where the extra budget went:

  • "Struck all seven xylophone keys in order", on a xylophone with eight keys;
  • "no such board exists … the four tiers cannot be assembled", on a layout where the program run built the tower;
  • "attempted roughly twenty grasps … Every close stalled at about 1.6 mm of fabric";
  • "wall_time_s is down to roughly 400 s of 40200" — the field is the time remaining; eleven hours were left.

More decisions bought more attempts of the same kind. They did not supply what the programs had: estimates that persist across turns, dense measurement at no turn cost, and a check right after each action. (The last quote is also a bug report against us: a budget field that a model can misread twice is badly named. We are fixing it.)

What the model builds for itself

Across all 59 program runs, the model writes a median of 58 Python files per episode and re-uses 7 of them in later turns. In 73% of turns that move the robot (1,305 of 1,789), the code that runs imports a module the model wrote earlier in the same episode. In the xylophone case, a scene.py written in turn 5 (key table, mallet-head finder) is imported by eight later files.

Some helpers reappear in run after run without anyone asking for them: cloud() in 32 episodes, pose7() in 25, tgt() in 20, measure() in 18, check() in 10. Others are one-off instruments for one task: a glyph-template matcher to read a digit's orientation, a 14×14 similarity matrix to find three matching tiles, a torque model to choose where to push a T-shaped block.

Can a program cheat?

A program can read files, which a tool call cannot, so we checked what it read. Each program runs in a bubblewrap sandbox with no network and no view of the run, the simulator or any credential; it cannot call the task checker. Read-only, it sees ORA's tool and motion source and the robots' public geometry. Simulator backends, task code and success checks are not mounted.

We audited every command of the 59 program runs. Programs in 26 cases read the mounted source, mostly to learn how a tool behaves. In five, they searched it for the task's name or for phrases of the instruction, and found only developer comments. None touched /proc, host paths, environment variables or the socket directly, and reading the source does not track success (7 of 20 solved cases, 19 of 39 failed ones). It remains an asymmetry: programs can read how the tools are implemented, tool calls only their descriptions.

What this does not show

The experiment is small: 59 paired cases, one episode each, on one benchmark. Several wins owe as much to strategy as to code; a block-alignment program used a ruler as a fence that the tool-call run chose not to use. Programs fail in their own ways: in the one case only tool calls solved, a single program pushed a block several times without checking and toppled it, while the tool-call run, forced to look after every push, kept it upright. Individual motions are not executed better either: 18% of program motions and 20% of tool-call motions end short of their target. What programs change is how much can be measured and checked per decision, and that matters most when success depends on a geometric estimate that has to stay consistent over many motions.

3. Different agents, different open models

The same model in other agent systems

Leaderboards mix model, harness and budget. To isolate the harness, we ran two other agent systems with exactly our model and settings (self-hosted DeepSeek-V4.1-Flash-1017, high reasoning effort, no simulator step limit) on our cases.

Uni-Robot-Agent in its strongest setting (Codex runtime with MCP robot tools; depth and SAM 3 on RoboDojo, RGB with triangulation on RoboLab, which is what its adapter supports). On the cases both systems finished, ORA solved more and used far fewer tokens:

Cases ORA Uni-Robot-Agent Prompt tokens per success
RoboLab 177 76.8% 63.8% 7.4M vs 53.3M
RoboDojo 72 48.6% 36.1% 24.6M vs 156.7M

The token gap is about the number of calls, not the size of each: Uni-Robot-Agent re-sends its full history on each of a median 229 (RoboLab) and 472 (RoboDojo) calls per episode, against 27 and 57 for ORA, whose programs measure, compute and act several times per call. Two caveats. ORA can query the task verdict on RoboLab and Uni-Robot-Agent cannot; RoboDojo, where neither can, is the fair comparison. And within RoboDojo's step limit Uni-Robot-Agent gets more official successes (16 vs 9 of 72), because each ORA motion takes about twice as many simulator steps (Appendix A).

RPent in its strongest LIBERO configuration, with the π0.5 VLA as its manipulation primitive and task memory from its own exploration. On LIBERO-Pro Task + Swap (391 cases finished by all arms), RPent solves 93.4% against ORA's 89.0% in code mode and 87.2% with tool calls. RPent has two things ORA does not use: a policy trained on LIBERO demonstrations, and memory explored on the same 80 tasks. Without its exploration, its tokens per success match ORA's (4.2M vs 4.1M); with it, they are 50% higher. ORA gets within 4.4 points with neither.

Appendix A: step limits and late successes

RoboLab and RoboDojo each define a limit on simulator steps per episode. We do not stop the episode there. We record the benchmark's verdict at the limit as the official outcome and let the episode continue; a success reached later is reported separately as a success after the limit. Our headline numbers count both. RoboTwin has no step limit and LIBERO-Pro stops at its own horizon, so every success there is official.

Benchmark Success, counting late Official only
RoboLab 79.2% 67.0%
RoboDojo 40.5% 10.5%

Why we count late successes. The step limits were set for learned policies that act at a fixed control rate. ORA is a turn-based agent: it measures, plans, moves and checks, and it spends simulator steps in places a policy does not (each ORA motion uses about twice the native steps of a direct joint command, and failed or retried motions add more). The late successes are real task completions by the benchmark's own check, and they show what the agent can do when time is not the constraint. They are not leaderboard numbers, and we do not present them as such.

How late. Measured as steps used over the official limit, the median late success lands at 1.57× the limit on RoboDojo and 1.70× on RoboLab.

Can a faster robot make them official? Mostly not. The default motion speed is already near the arms' joint limits on RoboDojo, and on RoboLab the model picks slower presets for most moves on purpose. Re-timing every move at the fastest preset would turn at most 10 of 60 (RoboDojo) and 3 of 61 (RoboLab) late successes into official ones. The steps go to extra decisions and stalled moves, not slow motion, so the way to convert late successes is to fail fewer moves.

Code mode and tool calls in the step-8 experiment. Of the 20 cases programs solved, 5 were within the limit; of the 6 cases tool calls solved, 2 were.
