Robots and tasks

Frames and units

For each environment ORA drives: the world frame, the point a pose command moves, the gripper axes, quaternion order, units, cameras, depth and control timing. The values match the robot manuals the model reads (for example ARX X5) and the default tool surfaces. A value marked not published is one ORA does not give the policy. For the message shapes that carry these values, see Policy I/O schema. For installation, see the environment pages for LIBERO, RoboTwin and RoboDojo.

Conventions shared by every environment

Quantity Convention
Positions World frame, metres
Orientation Quaternion [x, y, z, w]; normalized on input (norm 0.98–1.02 accepted, then renormalized)
Measured pose pose_xyz_xyzw: 7 numbers, position then quaternion
Angles Radians in canonical records, receipts and controllers. On the three default robot surfaces (policy_angles_degrees_v1) the copy the model reads states every angle in degrees. Inputs named rotation_angle_deg / angle_deg are degrees; rotation_rotvec_rad / rotation_vector_rad stay radians
Pixels OpenCV, origin top-left, u right, v down, native RGB resolution
Camera frame OpenCV: x right, y down, z forward
Intrinsics intrinsic_cv, 3x3, maps camera coordinates to native pixels
Extrinsics extrinsic_cv, 4x4, world-to-camera; cam2world_cv is its inverse, computed in plain Python so its digits do not depend on the host's BLAS
Depth float32 array, metres, optical-axis z distance (not ray length); delivered on demand to tools, not inlined each step
Calibration delivery Per observation, for every camera, fixed or moving

Each controlled point also has two local axes: approach (the direction the fingers point) and jaw closing line. The measured state carries their current world directions (axes.approach_world, axes.closing_world), so a policy does not need to rotate local axes itself.

Image size Not published in ORA

Control rate Physics 4 ms; 25 Hz control; one native action = 10 physics steps
Per command A move may use up to 250 native actions of the task's native-action allowance, other commands 20 or 30; the receipt reports how many were used, a refused command uses none
Arrival tolerance 0.01 m, 0.10 rad, gripper 0.03 (normalized); published each step in controller_feedback

Synthetic

Silent mistakes

Differences that break code written for one environment

  • The controlled point is not the same physical point. A RoboDojo pose moves link6, about 150 mm behind the jaw contact centre. A RoboTwin pose moves a TCP already 0.12 m ahead of the flange; LIBERO moves the grip centre. Code that adds a fingertip offset on every robot double-counts it on two of them.
  • Approach axes differ. Panda approaches along local +Z; ALOHA and ARX approach along local +X. A "top-down" quaternion copied from LIBERO points the RoboTwin or RoboDojo gripper sideways. Use the published approach_world and closing_world.
  • Gripper numbers are not apertures by default. Only LIBERO (measured_aperture_mm) and RoboTwin (gripper_opening_m) publish a measured separation, in different units. RoboDojo's 0.185 is an encoder floor, not 0 mm.
  • Internal gripper scales run in opposite directions. The measured opening is 0 closed / 1 open everywhere it is published, but the Panda motion profile writes open = 0.0 and close = 1.0. Send the named open / close directives, not numbers.
  • Angle units change between what you send and what you read. Default surfaces read back degrees, accept rotation_angle_deg in degrees, and keep rotation_rotvec_rad in radians.
  • extrinsic_cv is world-to-camera. Back-projection needs cam2world_cv. RoboTwin and Synthetic calibration files also contain cam2world_gl (OpenGL axes); do not mix it with OpenCV pixels.
  • A "tick" is not one duration. 50 ms on LIBERO, 40 ms on RoboTwin and RoboDojo, and on RoboDojo each tick also spends the task's native-action allowance.
  • Workspace envelopes differ in height. LIBERO z starts at −0.10 m; RoboTwin and RoboDojo start near the table at 0.70–0.72 m.
