Configuration and evidence

RunSpec and RunPlan

A RunSpec (ora.run-spec.v1) names experiment, config, milestone, task, task_instruction, seed, evidence_tier, output_workspace, policy, runtime and budgets. Additional qualification, session, prerequisite and launch-admission blocks are validated when selected, as are episode_mode and play (play episodes). The optional result_tier (default zero_shot) labels what the policy carried into the episode and is recorded in the plan; zero_shot_no_check resolves the baseline's allowlist without check_task, the tier must match the allowlist both ways on a surface that offers check_task, a free-play plan stays zero_shot, and with_experience and frozen_program are refused (result tiers). The optional latency_profile (default sim_benchmark; realtime) resolves to the explicit switches every plan records as latency_profile (latency profile). Resolution is implemented in ora/orchestrator/spec/run_spec.py and the section modules beside it in ora/orchestrator/spec/; the resolved plan is the exact execution contract.

Policy kinds are native_api and scripted. Native providers are openai_compatible and anthropic_messages. A Native policy binds an explicit endpoint/model, credential-variable names, context/output limits, tool surface, action codec and observation/context policy. The selected ToolSurface's capabilities and schema compatibility are validated together. memory_policy is disabled.

Agent core

policy.agent_core names the implementation that runs a native_api policy's agent loop (provider calls, request assembly, context management, agent-side evidence). Resolution is in ora/orchestrator/episode/agent_core.py:

Value Implementation Status
pi The TypeScript core in ora-pi/ on the exactly pinned Pi packages (@earendil-works/pi-* 1.3.0, undici 8.10.2), run by Node.js >= 22.19 under Node's permission model; Python serves tools, observations and authority (ora.agent.pi) The only agent core
native The Python Native core Removed from ORA (it remains in the robot-harness repository); refused

A fresh plan resolves to pi for every context composition and retention (native_slots_v3 with rewrite_compact_v1 or action_step_lossless_v4, native_slots_v4 with action_step_lossless_v4). A RunSpec with policy.agent_core: native, ORA_AGENT_CORE=native and --agent-core native are refused with the reason; pi is the only value either takes (--agent-core, on ora run, launch, validate, plan, context and preflight, is hidden and sets ORA_AGENT_CORE for one command). The resolved value is part of the plan and its plan_sha256, not of policy_identity.model_visible_sha256: the Pi core reproduced the Native core's requests byte for byte (the goldens in tests/data/agent_core/golden/ and the offline replays of the sealed acceptance runs), so a sealed Native plan and a Pi plan of the same RunSpec let the model see the same thing.

A persisted plan resolved for the Native core, one that records agent_core: native or one resolved before the field existed, does not start: building its session, preflight, ora play and the Pi terminal UI refuse it and say to resolve the RunSpec again. Its sealed evidence is unchanged and still evaluates, seals, opens in the viewer and replays with ora watch and ora replay, none of which selects a core. The names that carry "native" in that evidence stay: the policy kind native_api, the run's native/ directory, NATIVE_SLOTS_*, the ora.native-* schemas and the native-policy- session ids.

Preflight's agent_core check, and ora doctor, verify that the Pi core can start: a Node.js >= 22.19 binary (ORA_NODE, else node on PATH, ~/.local/bin/node, then nvm installs, newest first) and every runtime package of ora-pi/package-lock.json installed at its locked version. A failed check names the Node install command and npm ci in ora-pi; a session that cannot start the Pi core refuses with the same message.

Provider recovery

policy.provider_recovery decides how a failed model call is retried with the same credential. The Pi core applies it (ora-pi/src/provider/recovery.ts, transport.ts); the Python providers (ora/agent/providers/recovery.py, used by launch preflight's one-shot probes) implement the same decisions, and the agent-core parity tests compare the two.

Value Bound on one logical call Status
first_token_deadline_v1 No limit on the call's total duration. Each attempt must deliver its first stream event (for stream: false, its whole body) within provider_recovery_window_s (180 s when absent), counted from the attempt's start through connection and headers; after that event, no SSE line may be more than 180 s (STALL_S) apart. Either limit ends the attempt as a retryable transport failure. A stall follows content, so it is a stream break and spends the STREAM_BREAK_RETRIES (3) budget; first-token timeouts spend a budget of their own of the same size. An attempt that fails before its first event, for any retryable reason (HTTP 429/5xx, a transient connection or TLS fault, a first-token timeout), opens the no-content window, the same provider_recovery_window_s, when none is open; the window opens when that failure is seen. A failure before content is retried with the same backoff when its attempt started before the window's end, and raises its error when its attempt started at or after it. The decision goes by the attempt's start because the first-token limit equals the window: judged by when it is seen, a first-token timeout inside an open window would always end the call, losing the retry that recovers a request a restarting server dropped. Neither the backoff nor a Retry-After is shortened to fit the window, so the last attempt can start up to one backoff step, or one Retry-After, after the window's end. An attempt that delivers content (a reply, or a stream that broke after content) closes the window, and the next failure before content opens a new one. So an endpoint that refuses connections or answers 5xx is given up on about one window after its first failure; one that accepts and never answers after two retries, before the first-token budget is spent (that budget ends a call only when content separates its timeouts); and a restart of the endpoint shorter than the window, whether requests fail fast or hang during it, always gets an attempt after it ends. None is retried for the run's whole wall-time budget. Other failures keep the deadline policy's rules: HTTP 401/402/403 and certificate failures are terminal, 429 and 5xx back off (Retry-After, else 1, 2, 4 ... 20 s), a credential echo fails closed. Only the run's remaining wall-time budget bounds the call as a whole, ending it with ProviderRecoveryDeadline The default: every maintained baseline names it (native_full_explicit_motion_direct_v4 and robodojo_toolkit_v6, all moved from same_credential_deadline_v1), RoboDojo plans without a baseline inherit it, and a provider profile's recovery_window_s selects it
same_credential_deadline_v1 One fixed deadline, provider_recovery_window_s (180 s when absent), bounds the whole call: every attempt, its full streamed body and every backoff; when it passes the call ends with ProviderRecoveryDeadline, which is not retried Kept so that plans that name it still resolve, replay and verify; no maintained baseline names it since the two legacy-visible toolkit baselines that did were retired on 2026-10-31
legacy_v1 max_retries retries without a deadline; takes no window A RunSpec that names neither

provider_recovery_window_s (30..1800 s) is accepted with either deadline policy and refused with legacy_v1. A Python attempt runs in a transport subprocess; under first_token_deadline_v1 the parent also enforces both limits, 10 s later than the worker, and kills and reaps a worker that misses them (one stuck in a DNS resolver thread). Each failed attempt is a provider_attempt_failed event (ora.provider-attempt-failure.v1); under either deadline policy it carries recovery_policy and stream_break_retry_limit, and transport-phase records the running stream_breaks. Under first_token_deadline_v1 transport-phase records add the running first_token_timeouts and no_content_failures (attempts of the call that failed before their first event) with no_content_window_s, the no-content window; a failure before content adds no_content_elapsed_s, how long its window had been open when the failed attempt started (0.0 for an attempt that started before the window opened, such as the one whose failure opens it; the window allows a retry only while it is below no_content_window_s), and an attempt a limit ended adds attempt_timeout (first_token or stall) and attempt_timeout_s, the limit's length; partial_event_count says how many events had arrived. Records written before the no-content window carry no_content_retry_limit (8, a count of retries) in place of no_content_window_s and no_content_elapsed_s; they still verify and replay.

Context compactor

The rollout compactor writes the lossless retention's episode and emergency checkpoints, one tool-free call each (context assembly). By default it calls the policy's own provider and model. The optional policy.context_compactor binds it to another Provider profile, for example a small local policy model with its checkpoints written by an API model:

policy:
  context_compactor:
    provider_profile: deepseek_flash_openai_low_16k_v1
    provider_catalog: path/to/catalog.yaml   # optional

The field is opt-in and no default or builder sets it. A RunSpec without it resolves exactly as before, and its plan has no context_compactor key.

ora/orchestrator/spec/context_compactor.py resolves the profile as provider_policy resolves a policy's: built-in profiles first, then the user's providers.yaml, or only the named catalog (a project-relative or absolute path). The plan records, under the same key, the binding ora.context-compactor-binding.v1:

Fields Content
provider_profile, profile_source, provider_catalog The profile id; builtin, user or catalog; the catalog's {path, sha256} when one is named
provider, model, endpoint, endpoint_transport, reasoning_effort, stream, supports_images, context_window_tokens, max_output_tokens The profile's wire fields
base_url_env, api_key_env, proxy_env The profile's variable names; never a value
provider_recovery, provider_recovery_window_s A profile's recovery window selects first_token_deadline_v1 (provider recovery); otherwise the policy's provider_recovery
auth_scheme, output_token_parameter, reasoning_field, request_options, provider_session_affinity Only when the profile has them

The binding passes the same protocol and endpoint checks as a policy. It is part of plan_sha256 and of policy_identity.model_visible_sha256, because the checkpoint text it writes is what the policy model reads; the catalog's path and hash are masked there like every pin. Resolution refuses any other key under the field, and refuses a binding:

  • unless the policy is native_api with context_retention: action_step_lossless_v4 and summary_policy: rollout_checkpoint_v1, the only retention with a compactor;
  • in a free-play plan, where Pi compacts its own context;
  • for a text-only profile, since compactor packets carry images;
  • for max_output_tokens below 8,192, the compactor's fixed output ceiling;
  • for a context window smaller than the policy's;
  • for a gateway-bound profile (gateway_client_binding: true).

The Pi agent core runs a bound compactor (ora/agent/providers/compactor_binding.py, ora/agent/pi/factory.py, ora-pi/src/core/context_wiring.ts). Its calls use the binding's model, reasoning effort and stream, and a provider built from the binding: its own HTTP client, no standby keys, no retries and, when the profile has session affinity, its own X-Session-ID ora:<run_id>:compactor. What the compactor sees does not change: the same packets, the same private-evidence scan and the same 8,192-token output ceiling. The binding's provider supplies the checkpoint request options, as the policy's provider does for an unbound compactor (reasoning_effort: low and response_format: json_object for the DeepSeek models). A scripted or replayed session keeps its scripted compactor. Every context_compactor_* event of a bound compactor records provider_binding (episode evidence). Launch preflight probes the bound endpoint as compactor_provider_marker (runtime lifecycle).

Supported runtime kinds are synthetic, robotwin, libero_pro and robodojo. LIBERO and LIBERO-Pro both use libero_pro runtime kind with different source-paired task catalogs. Runtime inputs identify transport, simulator interpreter/source, task/seed/layout, renderer, control/motion profiles and execution resource as applicable.

Budgets bound robot decisions, model calls, simulation steps and wall time. Backend-specific limits may further restrict actions or physics steps. A model context window must leave a safe input margin after its output budget. Persistent rounds are explicit session inputs; they are not implied by task identity.

Use the maintained builders rather than copying a resolved plan:

./scripts/ora spec robotwin tasks
./scripts/ora spec libero tasks
./scripts/ora spec robodojo --help
./scripts/ora spec robocasa --help
./scripts/ora spec robolab compose --help

The builders take task/provider/host/resource inputs, exact qualification and service reports where required, and an explicit execution namespace/cohort. The default resolver selects native_full_explicit_motion_direct_v4, except on RoboDojo, whose default is robodojo_toolkit_v6 (robodojo_placement_toolkit_v5; a RunSpec naming no baseline also gets the surface's required check_task grant). A deliberate custom surface is recorded as such; registration alone does not make it the default.

The environment pages show one-cell recipes. ora baselines --explain previews the selected baseline and tool bindings. ora plan show RUN_SPEC shows the source, hashes, placement and budgets before launch.

RoboTwin and LIBERO cells

ora spec robotwin and ora spec libero (ora spec libero_pro is the same; ora/orchestrator/spec/benchmark.py) compose one RoboTwin cell, or one original LIBERO base suite or LIBERO-Pro core suite cell, on the default baseline. RoboDojo cells use ora spec robodojo (ora/orchestrator/backends/robodojo/spec.py).

  • ora spec robotwin tasks prints the RoboTwin roster with each public instruction and seed-named flag; ora spec libero tasks each base and core suite's ten task languages.
  • ora spec robotwin spec|compose TASK --seed N [--task-config demo_randomized|demo_clean] --qualification MANIFEST [--episode-names FILE] and ora spec libero spec|compose SUITE TASK_ID --seed N (a base suite such as libero_goal composes an original LIBERO cell, a core suite such as libero_10_swap a LIBERO-Pro cell), each with --experiment NS --resource-profile SLOT --service-report REPORT --cohort ID [--host HOST] [--provider-profile ID] [--provider-catalog PATH] [--config ID] [--milestone M] [--output PATH]. spec prints the RunSpec; compose writes outputs/NS/specs/<config>.json (or --output), imports the RoboTwin seed manifest under outputs/NS/qualification/seed-manifests/ and prints the spec path. A seed the manifest does not admit, a slot the host does not register for the backend, or a stale or re-pointed readiness report is refused before anything is written. It starts no simulator, service or Provider and grants no launch.

Official limit and the extended budget

A benchmark's official limit ends its published protocol, but a slow success is worth seeing. runtime.official_limit_multiple lets the episode run on to that multiple of the limit. Fresh RoboDojo, RoboLab and RoboCasa365 specs default to 1000 (TOOL_BUDGET_LIMIT_MULTIPLE, ora/contracts/official_limit.py; RoboLab and RoboCasa365 since 2026-11-05, when the user dropped the simulation-time limit; DEFAULT_OFFICIAL_LIMIT_MULTIPLE = 3 remains for a backend that sets none): the shortest RoboDojo task gets 200,000 native actions, past six hours of wall time, so max_robot_decisions, max_model_calls and wall_time_s end the run and no native-action count does. A success past the official limit is success_after_official_limit. The range is 1 to 1000, and 1 stops at the official limit. An absent field also means 1, so sealed plans and every qualification keep their stop. On RoboDojo the budget follows: build_spec(official_limit_multiple=...) and ora spec robodojo --official-limit-multiple set both the field and budgets.max_sim_steps (physics_step_ceiling(task, multiple)); a lower explicit max_sim_steps still binds first. max_robot_decisions, max_model_calls and wall_time_s are unchanged.

Backend Official limit What the multiple extends
RoboDojo step_lim in native actions (NATIVE_ACTION_LIMITS, 200 to 1900) the wrapper's native_action_ceiling; step_lim itself stays official
RoboCasa365 the evaluation horizon (450 to 4350 control steps, dataset_registry.py) the session's stop (extended_horizon); the environment is built with ignore_done=True
RoboLab episode_length_s at 15 Hz (750 or 900 actions) the Isaac Lab episode length; the official limit stays the roster's
RoboTwin step_lim (400 to 1700), counted per sparse decision nothing: 440 recorded runs used at most 141, so the limit does not bind under max_robot_decisions: 80, and the verdict is unchanged
LIBERO, LIBERO-Pro none: max_sim_steps is a Harness budget nothing
YAM a Harness tick limit, no benchmark nothing

The two results never share a field. official_success keeps its meaning, a success inside the official limit, so it compares with every earlier run; no report adds a later success to it. Under a multiple above 1 the verdict, the run or round record and evaluation.json add:

Field Meaning
official_native_action_limit The official limit, in the backend's native actions (RoboCasa control steps)
official_limit_multiple, extended_native_action_limit The plan's multiple and the stop it gives
official_limit_snapshot {official_success: false, native_actions: <limit>} when the limit passed without a success; null otherwise
success_after_official_limit True when the official predicate first held past the limit
success_after_official_limit_native_actions The native actions used at that success; null otherwise

The official predicate is the same on both sides of the limit and its evaluator is unchanged; only the field it lands in differs. RoboDojo's final check belongs to the official limit, so a task that registered one ends there whatever the plan allows; no shipped task does. A late success stops the episode, as an official success does. A multi-round session counts them in round_success_after_official_limit_count, beside round_success_count.

The ending says what ended the round. On RoboDojo a simulator ending past the limit is round_end_basis: official_terminal_transition with upstream_ending_condition success_after_official_limit, official_failure_latch, or native_action_limit at the extended limit only. A Harness budget or finish_episode that stops the extension is harness_budget_exhausted or policy_finished_episode, and leaves the result settled at the limit in place with verdict_basis: official_result_at_official_limit. Runs sealed before 2026-11-02 keep their records, where any false ending past the limit reads native_action_limit. A fault after the limit keeps its null verdict. run_report names the ending success_after_official_limit, keeps official_success false and counts these in successes_after_official_limit, outside successes and success_rate.

The policy sees neither the limit nor the snapshot. native_actions_limit and native_actions_remaining count down to the real stop, and RoboCasa's control_steps_budget and RoboLab's native_action_limit report that stop too. At TOOL_BUDGET_LIMIT_MULTIPLE no native-action count is a stop, so RoboDojo's remaining_budget leaves both fields out, as RoboTwin's does, unless an explicit max_sim_steps binds below it. Nothing happens to the episode at the official limit. A longer allowance can change behaviour inside the official limit, so a comparison of rates still states the multiple each side ran at.

Play episodes

episode_mode is benchmark (the default) or play, and only a play plan carries the key, so a benchmark plan's bytes and plan_sha256 are those of a RunSpec that never named it. A play RunSpec (ora play, experiment ora-play) loads one benchmark task's scene and initial state and nothing else of the task. ora/orchestrator/play/scenes.py owns the scenes and the backend bindings; spec/play.py resolves the play block (ora.play-session.v1):

  • play.scene is the current scene and play.scenes the /reset candidates, each with environment, task, seed and qualification (the record that admits it), plus scene_id, label and the LIBERO suite and task id or the RoboTwin scene configuration. A backend resets in place only to another seed or initial state of the same task and configuration. The task id serves the backend and the evidence; it is not policy input, and task_instruction is the session framing, never the scene's task language. The reviewed completion contract is withheld.

  • bind_play_runtime binds the plan runtime to the backend's play binding, which loads the scene with its official predicate withheld: LIBERO environment_driver: direct_libero_play_v1 (the BDDL _check_success reads false on the one problem instance, so no step reports success, reward or a success termination) and RoboTwin environment_signal_policy: play_scene_v1 (the task's check_success reads false, so eval_success never latches). Nothing a task would count as success ends or changes a scene; it ends at the operator's reset or quit, a budget or the environment's own step limit, and its verdict is official_success: null. A benchmark runtime cannot select either binding, and the baseline template refuses a RunSpec that names one itself.

  • Scenes come only from this host's records: the LIBERO-Goal and LIBERO-Object init-state files of the pinned LIBERO-Pro checkout (LIBERO_PRO_ROOT, bound by sha256, 50 states each), and RoboTwin seeds a local seed manifest admits for the task, its scene configuration and the pinned revision (backends.robotwin.seed_manifest.seed_admission; the plan binds that manifest, so preflight re-admits the seed). Synthetic is the built-in world. RoboDojo offers only ORA's own scene sets (below); its official tasks are not play scenes, because their success and failure latch inside the benchmark worker bridge.

  • RoboTwin also offers ORA's own scene sets, only when a play session names one (scene_set; ora play --scene-set, or --scene naming one of its scenes). A set's scenes (registry ora/environment/benchmarks/robotwin_play_scenes.py, worker-only modules in ora/environment/backends/robotwin/play_scenes/; tabletop-v1: table_setting_sequence, shell_game_memory_3, obstacle_rearrangement_6; household-v1: breakfast, kitchen; all on demo_clean) are Base_Task subclasses that place RoboTwin library assets and create_box primitives on the standard table, with no predicate (check_success is false), expert or instruction. A scene record carries scene_set, and bind_play_runtime binds runtime.play_scene_set beside play_scene_v1; the worker then builds the scene from ORA's module instead of envs.{task}, and the session's source manifest binds the set's ORA sources (play_scene_source) instead of envs/{task}.py. No other plan may carry runtime.play_scene_set, and a play session's scenes share one scene configuration and scene set. The RoboTwin checkout and its pinned revision are unchanged. A set's source binding covers play_scenes/base.py and its own module only, so an edit to one set's module leaves the other set's audits admissible. household-v1 (play_scenes/household_v1.py) builds each object itself (HouseholdScene.place), from the library model's collision and visual files at its calibrated scale (or the mesh's own units, as create_actor), or at an explicit scale for an asset without one (EXPLICIT_SCALES: jam jar, steamer, tomato, onion, cutting board), with a household mass (mass_kg, 0.12 to 0.60 kg), the inertia PhysX computes for the shape at 1000 kg/m³ scaled by the same mass ratio (RoboTwin's Actor sets 10 g and keeps that inertia), and static/dynamic friction 0.6/0.5 on its collision shapes (OBJECT_FRICTION; RoboTwin's library shapes have 0.3/0.3); no limit or material of the robot, the table or the scene changes. Its scenes frame the operator camera on their own (HouseholdScene.operator_view, merged over base.OPERATOR_VIEW). A scene-set scene also has ORA's operator camera (play_scenes/base.py: operator_camera, 1280 × 720, 44° vertical field, from the operator's side of the table at three quarters, ray-traced at 8 samples per pixel while RoboTwin's cameras keep 32), added to the SAPIEN scene after the objects and never to RoboTwin's camera manager, so no observation, point cloud or policy camera includes it; the operator view answers with it, and the execution capture records it beside head_camera and front_camera (PlaySceneTask.capture_images renders only those three, not RoboTwin's update_picture, which renders the wrist cameras too), rendering a frame only once the capture writer holds at most one queued frame (backends/robotwin/execution_capture.py, PLAY_CAPTURE_WRITER_BACKLOG; without the wait the writer, which shares the interpreter with the simulation, dropped 104 of 253 frames). build_play_spec sets a scene-set plan's runtime.execution_capture to {enabled: true, fps: 30} (robotwin_play_scenes.PLAY_EXECUTION_CAPTURE). After each action of a scene-set scene (each skill stage included) the session settles the scene (backends/robotwin/play_settle.py, entered from the execution-capture execute wrapper after the receipt is written and before the action's action_end capture frame): it steps the scene on with every drive target held, writing none, 10 physics steps at a time until over one window no dynamic object moved more than 1 mm or turned more than 1° (poses, not velocities), at most 500 steps (2.0 s), ignoring objects more than 0.44 m below the table top (fallen to the floor), and appends one line to native/post-action-settle.jsonl (ora.robotwin-play-post-action-settle.v1: action_id (a stage's parent action; the stage's own id as dispatched_action_id), action, action_sequence, round_index, physics_step_start on the capture's sim_step clock (physics steps since the round's reset), physics_steps, physics_dt_s, simulated_s, windows, ended at_rest or step_limit, moving_at_start, the first and last window's largest displacement and turn and the object that moved most, off_table, bounds and wall_s). The settle changes no receipt or observation, does not run the official-success latch (a play scene has none) and does not count toward take_action_cnt; a benchmark task and play on an official task never settle.

Identity and policy assets

source binds the exact Git commit and dirty state. Launch requires clean committed source. policy_identity records the policy-lock digest and model-visible digest. The plan identity also binds resolved configuration, source/version contracts and content references. Schema strings and asset paths are serialized data, so namespace migration changes hashes even when motion behavior remains the same.

policy_identity.model_visible_sha256 (ora/orchestrator/evaluation/model_visible.py) is one digest of what the plan lets the model see: the advertised tool definitions and result schemas, the text of each prompt layer, the embodiment card and its projected facts, the observation projection, and the policy, runtime and budgets settings with pins masked, plus the latency profile's model-facing switches that are off. It leaves out the episode identity, source, qualification, session and launch records, the policy keys that name the agent-loop implementation or restate another setting (agent_core, context_scheme, context_stages), where the run executes (runtime.resource_binding, required_host, cuda_visible_devices, renderer_gpu) and what the run records for people: a present runtime.execution_capture is compared as the recorder's default config ({enabled: true, fps: 10, queue_capacity: 32}), whatever it says, since only people read the frames (ora web, the Viewer, ora replay video). Every plan resolved with the default capture keeps the digest it was sealed with, and cells recorded at 2 fps or with capture off have the digest of the same cells at 10 fps. A plan sealed before 2026-11-06 with another capture setting (a free-play plan at 30 fps, a realtime plan) recorded a digest that included it; recomputed now, its digest is that of the same plan at the default. scripts/dev/compare-model-visible BASE CANDIDATE recomputes the same items for two commits across a fixed RunSpec matrix.

policy.lock pins tracked policy assets and catalogs in canonical sha256sum format. Run ora lock after intentional policy edits and commit the lock together. ora lock --check detects drift; ora lock --strip-pins maintains path-only assets and compiled embodiment manifests.

Host profiles name environment variables, not credential values or machine-local paths. ORA ships two generic profiles in ora/orchestrator/hosts/: local-cpu (ora local) and single-gpu (ora setup --env / ora run --env: one libero-gpu0, robotwin-gpu0 and robodojo-gpu0 slot on CUDA device 0; the slots are different resource classes, so one task at a time is that profile's operating rule, not a lease). A profile in ORA_HOSTS_DIR with the same id takes precedence. For any other host, copy examples/hosts/example-host.yaml to an ignored/local host directory and set ORA_HOSTS_DIR and ORA_EXECUTION_HOST. Exact simulator slots are registered in that profile. Host/resource placement is distinct from policy-visible composition.

World view and remote sessions

While a terminal is attached to a Pi-core run (ora interactive --ui pi, ora play, ora attach), the attaching command serves the run's world view (ora.orchestrator.world_view) on 127.0.0.1: read-only, bound to the run's native/execution-capture/, gone when the terminal detaches. It is on in a terminal or with --world-port/--world-public-url, off with --world-view off; the attach client receives its state on the pipe named by ORA_WORLD_FD and relays it to the TUI (world {state} in the attach protocol). Nothing of it is written to the run.

A command run by ora-remote carries ORA_REMOTE_SESSION=<command>-<16 hex> (derived on the laptop from host, checkout and command line). The run it attaches is recorded in .harness-runtime/ora-remote/<session>.json (ora.remote-session.v1: run id, run root, host name, time); the same play or interactive command then attaches to that run while its Supervisor is alive on the same host, unless ORA_REMOTE_FRESH=1 (ora-remote --new). The record is runtime state, not evidence.

With the TUI host (or ORA_PI_RPC=1), the agent process also serves Pi's RPC protocol (ora-pi/src/rpc/) and records native/pi-rpc.json (ora.pi-rpc-endpoint.v1: socket, pid, protocol: pi-rpc, pi_version, run id, start time), beside native/pi-tui.json; the socket itself is outside the run (the temporary directory, or /tmp when that path is too long). ora-rpc-attach takes ORA_RPC_RUN (the run) and ORA_RPC_ROLE (controller by default, or observer). ora web keeps its web server's log and sockets in a private /tmp/ora-web-* directory removed when it stops, reads the run's stored images (native/agent-artifacts/) and world view, and writes nothing into the run. ora replay reads a finished run's native/pi-session/*.jsonl, events.jsonl, agent-events.jsonl, native/execution-capture/ (manifest and timeline), native/post-action-settle.jsonl, the operator views and the stored images, in the same private temporary directory, and writes nothing into the run either; its export writes only the video and its report beside it (ora.replay-video.v1: size, frame rate, frames, duration, the camera box's shape, speed and motion speed, the seconds of robot motion, each stretch's rate with its video, recorded and simulated times, the replay's notes, and the run's ID unless published), with its frames drawn in the system temporary directory and removed. The display choice of the page (ora.web.display) and its language (ora.web.lang) live in the browser. The built page records the digest of the sources it was built from in ora-pi/web/dist/ora-build.json (ora.web-build.v1). ora-remote --web passes ORA_WEB_SOCKET and ORA_WEB_TOKEN_FILE to the attaching command; the token file (0600, in $XDG_RUNTIME_DIR/ora-remote/, else ~/.cache/ora-remote/) is removed when read, and files there older than 12 hours are swept by the next session. Neither the token nor the cookie is logged.

Free play

ora play (guide) resolves a plan with episode_mode: "play" (a benchmark plan carries no such key) under the ora-play experiment, with operator_control and a play block (ora.play-session.v1):

  • scene is the scene the run starts in: environment, task, seed and qualification, with scene_id, label and the LIBERO suite and task_id or the RoboTwin task_config (and scene_set for a scene of ORA's own RoboTwin or RoboDojo scene sets), from ora.orchestrator.play.scenes.build_play_spec;
  • scenes lists the scenes reset may load in turn, 1 to 32 of them, starting with scene, all on the plan's task;
  • instruction_budgets holds max_robot_decisions, max_model_calls and wall_time_s, each at most the session's budgets;
  • context_images (default {"observations": 3, "tool_results": 3}, each 1 to 50) is how many of the latest observation messages and tool results with images keep their images in a model request. Pi's context hook (ora-pi/src/play/context_images.ts) replaces every older image of that request, never of the session, with one text line naming its observation step and camera, or its tool; images the operator attached are always sent, and the play_provider_request artifact is the request as sent. Sent in full, a long session outgrew a provider's body limit (HTTP 413 at 50.8 MB);
  • draw records how the scenes were drawn.

A session block is refused, and so is a plan naming the retired native agent core. Free play runs on the Pi core. The plan runtime is the scene's play binding (play.binding.bind_play_runtime), which loads the scene with its official predicate withheld and which a benchmark plan cannot select; a RoboTwin scene's seed manifest (or, for a scene of a scene set, its play-scene audit, with runtime.play_scene_set) and a RoboDojo scene's play-scene audit must be the one the plan binds.

The Pi core runs a free-play act as Pi's own agent (ora-pi/src/play/).

  • Pi: the user's Pi configuration (PI_CODING_AGENT_DIR or Pi's default), Pi's coding tools with the run's sandbox/workspace as their working directory, Pi's context and compaction, and Pi's model registry. The ORA provider profile is registered as provider ora. Its request_options are the ora model's sampling parameters, so every request Pi builds for that model (a turn, compaction, a branch summary) carries them, validated and refused as an episode's provider validates them, and no other provider's model does. A profile that names its own reasoning object has Pi state the reasoning effort as reasoning_effort, as the episode provider does. A Pi models.json that overrides the ora model's sampling ends the start.
  • Robot tools: they stay Python tools. A world-changing call ends Pi's run, and the Supervisor executes it.
  • Scripts: Pi's codemode tool is on, without its models global. A codemode script's robot call reaches the run's robot socket, as ora-robot from the shell does: the Supervisor runs it inside the turn, and the trace records it with payload.origin.kind codemode and the codemode call that made it (parent_tool_call_id); the socket names a call codemode only when the agent process itself made it. A script's other nested calls carry the same origin.
  • Credentials: the agent process gets the user's environment minus credential-shaped variables. /login writes the user-level store ($ORA_CONFIG_HOME or ~/.config/ora, file pi-auth.json) in every mode, the store ora providers keeps ORA's keys in; a benchmark run reads it once into memory.
  • Restarts: the agent process is not restarted.

The Supervisor (episode/play.py) adds an awaiting_instruction phase to the interaction state. The operator inbox also admits instruction, queued_instruction, stop_instruction, reset and quit. A queued_instruction sent while an instruction runs is held until that instruction ends and then opens the next one (announced as message_queued_next); with no instruction running it opens one at once. Its operator_message event keeps type: queued_instruction and counts as an instruction.

  • Instructions, and the messages the operator sends while one runs, are delivered as operator_message events (type: instruction) before the next model call. Controls are recorded as play_control events and acknowledged.
  • Each instruction is a play_instruction_started / play_instruction_finished pair (ora.play-instruction.v1). The pair records ended, decisions, refused_proposals, model_calls, the observation steps and the wall time.
  • A new instruction starts on a fresh observation, published before its first model call through the opening scene's path. The policy-state snapshot has cause instruction_start, beside reset and after_action. The started record's observation is {"fresh": true, "observation_step": N}. When the look fails, it is {"fresh": false, "observation_step": N, "error": ...}: the instruction runs on the last observation (step N), an auxiliary_failure (stage play:instruction_observation) is recorded, and the instruction's operator_message payload carries the observation_note the model reads after that observation. A message that joins a running instruction takes no new observation. Records written before this change carry no observation.
  • A message sent while an instruction runs joins it: the instruction's record lists it in joined_messages, and only the first message of an instruction opens one. Evaluation requires every delivered instruction-type message to have opened an instruction or joined one. Records written before this change carry no joined_messages; in them a newer instruction ended the running one as superseded.
  • A text-only reply that is the model's first reply after it read a joined message is that message's answer, not the instruction's report. The Pi driver knows which model call first read each joined message (Pi steers a message in after the current tool batch, so that may be the next act's first call: PlayDriver.noteContext from Pi's context hook) and names the messages a text-only last reply answers in the act outcome (answers). The Supervisor records a play_answer event (ora.play-answer.v1: instruction_id, instruction_index, message_id, observation_step) for each answered message that joined the running instruction and has no answer yet, lists it in the instruction record's answered_messages, and keeps the instruction running: the next act brings the same observation. Each joined message earns at most one continuation; a text-only reply that answers no newly read message is the report (ended: reported). Evaluation requires each play_answer to name a message its instruction lists in joined_messages, once, matching answered_messages (play_answer_invalid).
  • A reply the provider's output limit cut off before any tool call (stopReason: "length", with or without text) is no report. As in an episode (afterTruncatedOutput), the Pi driver records a derived provider_output_truncated event (tool_call_count: 0, text_chars, policy_outcome) and, from Pi's turn_end, adds ORA's continuation as an ora.continuation custom message (details.ora_reason: "output_truncated") that the next model call reads on the same observation (a joined message the cut-off call read first counts as read by that call for its answer); that call's boundary still checks the operator's inbox and the instruction's budget. When the act's own model calls or time (the session's remainder) are spent, the act ends with termination output_truncated and the Supervisor ends the instruction ended: output_truncated (policy_outcome: "output_truncated"); an act that ends on a cut-off reply is never policy_no_action.
  • The instruction's model calls and wall time are checked before every model call.
  • A scene change is a reset event and a play_scene_reset event. A scene the environment ends (play_scene_ended) waits for reset or quit.
  • No official verdict is persisted.

Operator view

An environment session may give the operator a better picture than the policy's cameras, for example a third-person camera. It is the operator's alone: no observation, context, tool result, agent event or provider request carries it.

  • Session contract (ora/environment/base.py): an optional method operator_view() -> {"png": bytes, "camera": str, "width": int, "height": int} | None. png is one PNG image (at most 8 MiB) whose IHDR size equals width × height (each 1 to 8192); camera is a short name ([A-Za-z0-9_.-]{1,64}). None means no view now. A session without the method has no operator view. The method must not advance physics, change the scene's random state or touch anything the policy observes.
  • Transport: DescribedEnvironmentSession.operator_view() forwards and validates it (validate_operator_view). Over the local worker transport (local_rpc), the worker writes the PNG to native/.operator-view-transfer.png and the client reads it back and removes it; the image never travels inside the JSON line.
  • When: a free-play Supervisor asks after each published observation (the reset, every action, every script action, every scene reset), once the policy has that observation.
  • Evidence: the PNG goes to native/operator-view/<observation_step:06d>.png and events.jsonl gains {"type": "operator_view_frame", "observation_step", "path", "camera", "width", "height", "sha256", "time"}; the live port gets the same record as an operator_view_frame event. Play evaluation requires each named file to exist with its hash (play_operator_view_frame_invalid). A failing view is an auxiliary_failure (play:operator_view); after three in a row the session stops asking.
  • Backends: Synthetic draws a front view of its arms (operator_front_view, 640 × 400) when its execution capture is on. RoboTwin returns its observer_camera (320 × 240), and a scene of ORA's RoboTwin scene sets its own operator_camera (1280 × 720, also an execution-capture camera; see the scene sets above). A RoboDojo play scene returns operator_camera (backends/robodojo/play_scenes/operator_view.py): a USD camera 1280 × 720 (15 mm lens, 16:9) looking at the table at three quarters from its far side, with both arms in frame, attached after each reset and released before a relaunch closes the stage, never registered with RoboDojo's camera or capture manager; the play session reads its Replicator annotator's latest frame without rendering, and by default records it as a fourth execution-capture camera beside head, left_wrist and right_wrist, its frames tagged with the executing action's id. The worker-config field operator_view_mode (capture, the default; view; off), which no plan can carry, exists to measure its rendering cost; the play source manifest records the mode and the camera. LIBERO has none (its environment renders only the policy's cameras). A backend that also lists the view's camera among its execution-capture cameras gets live and recorded motion in that view too (the web page plays motion for the view's camera when the capture has it).

What the operator's clients see is display only and never evidence:

  • Announcements (ora.play-state.v1, to the live port, the TUI and Pi RPC clients): besides instruction (now with message: {id, text, instruction}), instruction_finished, control, scene, scene_ended, awaiting_instruction and ended, the Supervisor announces message_queued (a message admitted while an instruction runs, which will join it), message_delivered (message: {id, text, instruction, joined, observation_step}), action_started and action_finished (action: {action_id, observation_step, duration_s}), the robot executing an action of the policy or of a script, and answer (answer: the play_answer record; the instruction keeps running, so no instruction_finished follows it).
  • Delivery records: each free-play operator_message payload also names instruction_id (the instruction it opened or joined) and joined.
  • Pi's conversation: a joined message reaches Pi as a custom message ora.play_message (a user message on the wire, the operator's words only; details = {ora_message_id, ora_instruction_id, ora_instruction, ora_observation_step, ora_joined} for the terminal and the page); the instruction stays Pi's user message.
  • Language: the TUI's ORA words follow ORA_UI_LANG (zh or en), else a zh* locale; the web page follows the browser (ora.web.lang in its local storage once chosen).
  • Demos: ORA_SYNTHETIC_ACTION_WALL_S (0 to 10, default 0) makes each Synthetic action take that many wall seconds, its world capture paced in real time, so a demo shows the robot moving.

The agent trace adds these events: provider_request / provider_response (with the provider and model each call used), tool_call_proposed / tool_result for Pi's tools, operator_shell_command / operator_shell_result, model_selected, thinking_level_selected, conversation_compacted, conversation_navigated and conversation_switched.

The result carries play (instructions, scenes, control count), official_success: null and behavioral_sample_valid: false. Evaluation checks those records against the events (evaluation/play.py), and it checks the agent trace for completeness only (ora/agent/evidence/play_trace.py: the hash chain, artifacts, a response for every request, a result for every tool call, a receipt for every action). LIBERO planner world model

runtime.motion_planner.world_model selects what the LIBERO CuRobo planner collides with. none plans against the robot alone: joint limits and self-collision; no maintained baseline selects it since the provider-tape replay baseline native_full_explicit_motion_direct_replay_v1 was retired on 2026-11-01. public_depth_voxel_v1, the default baseline's since 2026-10-30, adds a voxel world built for every request from public depth only (ora/environment/controllers/depth_world.py): both cameras' metric depth and calibration, the measured base pose, joints and fingers, and the planner's own robot spheres; no simulator state and no segmentation. The world removes the robot's own depth, carves the measured start and an oriented box around the goal hand (hand and fingers to about 1 cm past the fingertips, and a 5 cm approach standoff), moves the held load from the world to the hand, and is loaded as a 1 cm ESDF. The grid covers x -0.20..1.01, y -0.60..0.61 and z -0.25..0.76 m in the robot base frame; CuRobo's voxel kernel reads the outer three voxels of each face as unobserved (free), so the loaded grid is that volume grown by three voxels per face around the same centre. Plans and the reach check's IK both use the world, each goal in its own carved world. depth_world.curobo_v2_grid exports the same world for cuRobo V2, whose voxel kernel reads distances negative inside, as float16, from round(dims / voxel) centred voxels per axis with no unobserved border (a query outside reads free): the export is the volume above without the border (121 x 121 x 101 voxels of 1 cm, centred 5 mm past the grid centre on each axis, so that V2 voxel i is the v0.7.8 voxel i + 3 at the same centre), with the sign flipped. Both kernels see the same occupancy; sha256 hashes the export's layout and values (ora.curobo-v2-voxel-grid.v1). Replay is unaffected: it reads the recorded joint commands.

The two-arm robots carry their own parameters (ROBOT_WORLDS). RoboTwin's ALOHA uses PUBLIC_DEPTH_VOXEL_ALOHA_V1: the depth of the policy's four cameras as get_obs publishes them at the request, read without advancing physics, a 1.46 x 1.86 x 0.86 m grid centred at (0.45, 0, 0.25) in the arm's base frame, and the other arm's spheres at its measured joints in the world.

The default LIBERO surface (libero_placement_direct_overhead_v1) describes this world to the policy. Its move_pose help says that global CuRobo routes and every IK check avoid a world rebuilt per request from both cameras' depth, with the robot removed, the goal hand's region cleared, a held object moving with the hand and unseen space free; that a target with a fingertip more than 1 cm below the supporting surface is refused before planning; and that the bounded local OSC segments do not check the world. Its grasp_plan IK selection names the same solver. The text changed in place on 2026-10-30 (the depth-world sentences, then of the layer published_limits_v1/libero-overhead-help.json and now of the file-backed surface's explicit_motion_v3/move_pose.json); a sealed run keeps the tool definitions its plan recorded. The reach check answers with the planner's world model: ik_model: libero_reach_ik_depth_world_v1 and the depth-world claim_boundary in world mode, libero_reach_ik_robot_only_v1 and the robot-only claim under none. The new texts name behaviour ("the global planner", "the IK check") rather than the planner library, so the planning backbone can change under them; the planner binding and evidence keep naming the exact implementation and version. The planning-diagnostics note likewise reads "Self-collision and the depth collision world are not separated." or "World collision model is absent.". The delivery trim (observation_delivery_trim_v2) leaves a fixed claim_boundary, evidence_scope or note text out of a result or action effect only when a tool description delivered in the same run states it word for word (trim.stated_prose over the session's delivered tool list, in the written or degree form). The table of such texts (ora/agent/context/delivery/trim_prose.py) keeps both LIBERO forms: today's help states the depth-world texts, so a none run keeps its robot-only claim and note in each result, while a sealed run replayed with the definitions its plan recorded, whose help states the robot-only texts, has them left out as it did when it ran. A text edited in place keeps its old form in that table, with no backends, for the same reason.

On LIBERO grasp_plan adds a top-down fallback (panda_public_rgbd_topdown_fallback_v1, agent/toolkit/host/grasp/panda_topdown.py). Backend id contact_graspnet_then_panda_rgbd_topdown: when Contact-GraspNet returns no candidate, up to two top-down candidates are given instead, with the support-aware height rule from the target mask and scene depth, pads centred on the grip site and fingertips at least 5 mm above the support. They are never shown beside learned candidates, so a call the network answers is unchanged. A target too sparse for this family costs only this family. diagnostics then uses the two-family shape (learned, public_rgbd_topdown, candidate_family_counts). On the recorded inputs of 222 LIBERO calls, 24 of the 29 calls with no candidate get one; the other 5 exceed the 80 mm opening. RoboCasa365 and RoboLab do not declare it.

Neither carve box clears the support under its hand: the dominant horizontal surface found from the depth within 15 cm of the fingertips (the lowest level that tops at least 100 grid columns, so the table rather than an object standing on it). A goal with a fingertip more than 1 cm below that surface (support_tolerance_m, which absorbs the depth noise in the surface height) is refused before any solver runs: a plan answers refused with goal_below_support and a planning-diagnostics recovery line that says how far below the surface the fingertips are, and an IK query is unsolved without a solve. A goal within the tolerance goes to the solvers with the support still in the world, so it reaches only as far into it as collision allows. The goal carve's spheres (a held load's, swept over the standoff, and a joint goal's robot spheres) leave that support too. Held spheres over-cover their load, so the ones attached for a goal stop one voxel above the support, and a load set down on it plans. When the load's own seen points lie more than the tolerance below the surface, the spheres stop at those points instead, in the support, and the solvers refuse the goal. A start's spheres do clear the support, because a measured start must be free. When the arm hides the table within 15 cm of the fingertips, the support is found over the whole grid. A load is held while the gripper is commanded closed and its jaws stopped between 3 mm and 7.5 cm apart (the world inputs carry no jaw-stall outcome; jaws at the Panda's 8 cm never closed). It is the set of occupied voxels connected to the depth between the jaws above the support, within 15 cm of the pad slab and never through the slab of a support below them: the whole object and none of the table under it. A component that reaches that 15 cm bound is joined to the scene (a container or shelf the object touches), so then only the depth between the jaws is held and the rest stays world (held_component: seed_only, otherwise whole). So is a component that reaches more than held_overhang_m (6 cm) past the jaws along the closing axis and stands on that support in at least held_rest_columns (40) grid columns, within two voxels of its top: a held object touching a cup on a plate. Width alone does not say, because a bowl held by its rim reaches 13 cm past the jaws, so such a load stays whole once it leaves the support; the move that lifts it plans with only its middle held. The held voxels leave the world and at most 32 spheres fitted to them are attached to panda_hand.

Every request loads its own world and restarts the planner's seeds, so no earlier request changes its answer. The world itself (world.sha256) is exact, and replay reads the recorded joint commands without a planner, so a sealed run replays exactly, whichever planner recorded it.

The client (MotionPlannerClient, ora/environment/controllers/motion_planner.py) starts the worker with --world-model, checks that readiness reports the same model, records it in the planner binding (world_model, so a plan reference's source identity changes with it) and refuses a request of the other mode before sending it. Motion planner contract

Backends ask their planner through one planner-neutral contract (ora/environment/controllers/motion_planner.py), so the planner behind it can be replaced. A plan request (ora.motion-plan-request.v1) carries robot (franka_panda), start: {joint_names, joint_positions}, a goal that is either {tool_frame, pose_base_xyzw} (the tool frame's pose in the robot base frame, xyzw quaternion) or {joint_positions}, world ({model: none} or {model: public_depth_voxel_v1, input: {path, sha256}}), held_object ({source: none}; {source: world}, the load the world builder finds between the jaws; or {source: spheres, spheres_tool_frame}) and constraints (reserved; empty). An answer (ora.motion-plan-answer.v1) carries status (planned, refused or error), reason, trajectory (joint_names, positions, velocities or null, dt_s), start_tool_pose_base_xyzw, world (model, sha256, inputs_sha256 and the world's summary), planner (implementation, and whatever identity the implementation adds), timing_s (total and its parts), the request it answers, and detail, the implementation's own evidence; a goal_unreachable of a pose goal in a world has detail.goal_diagnosis, below. A refusal names one reason: goal_unreachable (no IK solution in the world), goal_in_collision (a joint goal touches the world or the robot), goal_below_support (the world refused the goal before any solver ran), start_in_collision, start_outside_limits, or path_blocked (a valid goal without a collision-free trajectory, or with only a trajectory the path check below refuses). An error is planner_error or timeout and says nothing about the goal. A planner library's own status names appear only in detail. IK requests and answers (ora.motion-ik-request.v1, ora.motion-ik-answer.v1) chain queries: from_index seeds a query from an earlier one's solution, and a query whose seed failed is skipped; a result adds refusal: goal_below_support when the world refused its pose before a solve.

An implementation is a worker started as python -m <module> under its own interpreter (IMPLEMENTATIONS); it speaks ora.motion-planner-protocol.v1, one JSON object per line: ready, plan, ik and close. prepare (ora.motion-prepare-request.v1: robot and one or two worlds, each {start, world}; answered ora.motion-prepare-answer.v1 with status prepared or error, prepared and timing_s) has a worker build the goal-independent scenes of those world inputs before a request needs them; it answers no planning question, and a failed one is an answer, never a retired worker. The client serializes its exchanges (one lock), so a backend may send prepare from a thread of its own, and never starts a worker for it. The cuRobo V2 worker keeps the last two scenes (SCENES_KEPT, one per arm of a two-arm robot), each with the world inputs it was built from, so a request for one arm no longer rebuilds the other's; a kept scene is the one the same input builds again, so no answer changes. RoboDojo prepares both arms after each observation (backends/robodojo/shared_motion.prebuild): the two world snapshots are written on the simulator's thread when the observation is published, and a thread of its own sends one prepare per arm while the policy decides, the arm whose joints moved since the last observation first, so a request that arrives before both are built waits for at most one; a newer observation supersedes the arms not yet asked. Each prebuild is a line of native/motion-planner/prebuild.jsonl (observation_id, status prepared, superseded or error, arms: per arm asked arm, status, reason and timing_s, or error, and wall_s); a prebuild that fails leaves every request to build its scene as before. MotionPlannerClient checks the source (a clean checkout at required_revision, first on the worker's PYTHONPATH), records the binding (ora.motion-planner-binding.v1: implementation, revision, python and python_sha256, root, device, robot, world_model and the worker's readiness identity), refuses a request of another robot or world model before sending it, and retires a worker whose answer times out or breaks the contract. planner_client builds this client from a runtime.motion_planner block, which must name its implementation. motion_planner.planning_diagnostics gives a neutral answer the ora.planning-diagnostics.v1 feedback, with the reason as its outcome and the recovery lines, led by refusal_message, the sentence that says why: goal_refusal.message or goal_diagnosis.message. Every backend carries it to the model: LIBERO and RoboTwin in the arm's planner.planning_diagnostics, RoboCasa and RoboLab in the receipt's planning_diagnostics, RoboDojo as the refusal's own message. An implementation that keeps its IK seed populations puts them in detail.ik_attempts, one record per IK attempt (status: captured, each seed's joints, position and rotation errors, feasible, converged, accepted, returned_success, outside_position_limits, and candidate_counts and rejection_counts); the diagnostics then carry the last captured attempt's counts with details_available: true and evidence_scope: last_recorded_original_ik_attempt.

cuRobo V2 planner worker

ora/environment/planners/curobo_v2/ implements the contract on cuRobo V2, the cuRobo the RoboDojo SDK uses (IMPLEMENTATIONS["curobo_v2"]). The worker runs under an interpreter with V2's dependencies (torch, warp, cuda-core), with a clean V2 checkout first on PYTHONPATH. It holds one MotionPlanner (IK, trajectory optimisation and graph search on one scene collision checker) and one RobotCollisionChecker on that checker and the same robot model, so a start or goal check, an IK query and a plan see the same world and the same held load. The robot is V2's bundled franka.yml with ORA's changes (ora/environment/planners/curobo_v2/robots.py) and 32 sphere slots on attached_object. LIBERO simulates robosuite's PandaGripper, whose finger collision mesh has the same vertices as the Franka description's but sits 6.5 mm closer to the hand: robosuite mounts the finger 0.0524 m from right_hand, which lies 0.5 mm behind V2's panda_hand at the same joints, where the Franka description mounts it 0.0584 m from panda_hand. So the simulated finger ends 0.1057 m from panda_hand, 2.3 mm past the 0.1034 m fingertip point, while V2's bundled finger spheres reach 0.1124 m. ORA keeps V2's fit of the finger (two 11 mm spheres per finger) and moves it 6.5 mm toward the hand; every sphere, the fingers' included, keeps the v0.7.8 planner's 4 mm buffer (V2 ships 0). The lowest finger point is then 0.1099 m from panda_hand, 4.2 mm past the simulated fingertip, instead of 0.1164 m. The rest of the robot equals v0.7.8's, but the fingers differ, so the world built from the same snapshot (which removes the robot's own spheres from the depth) could differ from the retired v0.7.8 worker's and has its own sha256. Every answer's planner carries robot_sha256 (the whole robot configuration) and collision_spheres_sha256 (the sphere set: every collision link's spheres, the buffer and the held-load slots), and the readiness identity carries both and ORA's changes. The settings are the v0.7.8 LIBERO planner's: 32 IK and 4 trajectory seeds, up to four attempts with graph seeding from the third, 5 mm / 0.05 convergence tolerances and 0.02 s interpolation. The world is one voxel layer in a fixed-size cache, filled for each goal from depth_world.curobo_v2_grid, and the world summary adds planner_grid_sha256, the hash of the exported grid. CUDA graphs are on; switching between pose and joint goals re-captures them, which the worker enables as the SDK does.

The X5's joints 1 to 5 are +/-10 rad in X5A.urdf and in the simulated ARX.usd, a placeholder that let IK answer a whole turn away. The planner keeps them to X5_JOINT_LIMITS_RAD (planners/curobo_v2/robots.py, through position_limit_clip): 3.7, 3.5, 3.9, 2.4 and 1.56 rad. Joints 1 to 4 take the smallest half-range holding both the arm's rated range and every measured start, but for joint 1's runs wound a whole turn on routes with no planner (476 of 468,584 records; holding them would keep every alias). Joint 5 stays under the stop the simulated arm meets near 90 degrees either way, with self-collisions on: a plan past it ends in a tracking stop. Joint 6 keeps the file's +/-3.14 rad. cuRobo clips both ends alike, so joints 2 and 3 stay legal below zero, where the arm itself is not. This binds the shared planner only: the simulator and the straight and joint routes keep their own limits. A measured start past a limit gets start_outside_limits, and RoboDojo's lib/motion_plan takes that move by the joint route (plan_global, as with no planner), which can bring the arm back into range; that route may still refuse its own move, and nothing has moved then. return_home keeps its own screened joint line when the planner does not answer.

A measured start joint at most START_LIMIT_SLACK_RAD (5 mrad) past its limit is the arm resting on its stop, not outside the range: the worker plans from START_LIMIT_INSET_RAD (1 mrad) inside the limit and names each such joint in detail.start_inside_limits (joint, measured, planned_from), so the path's first row differs from the measured joints by at most 6 mrad. LIBERO's Panda parks joints 2, 5, 6 and 7 on their stops (0 to 0.2 mrad past), which V2 read as outside its limits: on 465 recorded LIBERO requests 29 were refused that way, some runs with every later move refused; planned from inside, all 29 plan and 24 turn the hand no more than they ask. A start further out still gets start_outside_limits.

A plan is then read against what its goal carve took. The carve clears the hand box at the goal, back past the wrist, and the planner sees that one grid from the path's first row, so a wrist, a wrist camera or an arm link could pass through a wall the world no longer held and stand in it at the goal. path_clearance.py measures each row's spheres, the attached load's too, against the scene with no goal carve; a path deeper than one voxel (TOLERANCE_M, 1 cm) is measured again in FingerScene, whose carve stops where the fingers begin (FINGERS_FROM_M, 0.05 m along the approach) and whose joint goal clears only the fingers' spheres. A path that passes either is the plan as the planner gave it. One that fails both is planned again in the finger world; when no plan stays clear the answer is goal_unreachable with the usual diagnosis, goal_in_collision, or path_blocked with detail.goal_diagnosis of cause path_in_collision (link, part, penetration_m, before_goal_m, and a message naming the point "in world coordinates" and what stands there: the other arm, the supporting surface, or what the depth shows). detail.path_clearance and the world summary's path_clearance keep status (clear, replanned, blocked), clearance_m, row, link, radius_m and point_base_m; timing_s adds path_clearance. A contact path's check (ora.motion-check-request.v1) uses the same finger world. An IK query solves in the goal's whole carve and then reads its solution as the one row a plan to the pose ends on: one deeper than TOLERANCE_M in the scene with no goal carve and in the finger world is solved again in the finger world, and answered unsolved (a reach check's ik_failed) when none there is clear, so a reach check holds what a plan to the pose would; the query's world summary is the world the answer holds for and keeps path_clearance (clear, replanned, blocked). On a desk play scene the IK alone had answered solved for two poses whose plans were refused, the hand 4.9 cm inside a stapler's depth that only the carve took (tests/data/planners/desk-stapler-reach.npz). The check knows only what the depth shows: rows near the start stay inside the start carve, and an object out of sight is not in any of these worlds.

A pose plan is then read by the pacing's wrist rule (motion_pace.check_unwind, on the pacing's joint grid with the tool frame's kinematics) and compared with straight joint lines from the start, spaced JOINT_GRID_SPACING_RAD apart, that reach the same pose: same_goal, to the plan's own last row, when the plan turns the hand more than MAX_UNREQUESTED_TURN_DEG (45 degrees) beyond its start-to-goal turn; alias, for every plan whose goal has a joint more than half a turn from its start with a 2 pi equivalent inside that joint's limits (each such joint moved to its equivalent nearest the start: the same link poses; only the ALOHA's +/-4.2 rad leave room for one); ik_pool, when the plan turns past the rule, to the other IK solutions of the pose in detail.ik_attempts (the converged, feasible seeds inside the limits, each at its nearest equivalent, counted once, the POOL_LINES (8) nearest the start). The candidates and, when the rule accepts it, the plan (planned) are ranked within the rule first, then by the smallest path turn, the plan winning a tie, rather than in the order the planner found them. The first line in that order that passes the planner's own checks (every row inside the joint limits and clear of the robot itself and of the goal's loaded world, by the start and goal check; the whole line, the attached load included, within TOLERANCE_M of the world a joint path to that goal is read in, FingerScene as a contact path's check reads it) is the answer's trajectory, at rest at both ends and at the plan's dt_s. A line the rule refuses is never answered. detail.wrist_detour (and the world summary's wrist_detour) keeps status (replaced, kept), chosen (the source answered, planned, or null), max_unrequested_turn_deg, planned (its path_turn_deg and requested_turn_deg) and candidates, each with source, its turns, goal_joints for a goal other than the plan's, and outcome (chosen; unwinds; blocked with blocked: check planner with the row and its check costs, or world with the path clearance; ranked_lower, never checked); timing_s adds wrist_detour for every pose plan. A plan within the rule with no equivalent goal nearer leaves no record. Joint goals are never read this way.

Per goal the worker loads the goal's world, attaches the held spheres, resets every seed, and refuses in this order: the world's refusal (goal_below_support, no solver runs; never in the worker's kitchen scene, ORA_PLANNER_SCENE, which ready names), a start outside the joint limits (start_outside_limits), a start touching the world or the robot itself (start_in_collision), a joint goal outside the limits (goal_unreachable) or in collision (goal_in_collision), a pose goal no IK attempt solved (goal_unreachable), anything else not planned (path_blocked). A goal_unreachable in a world then solves IK once more with nothing in the way and keeps why in detail.goal_diagnosis (cause, a message and, where it applies, link, part and penetration_m): out_of_reach when that solve fails too; robot_in_collision or held_object_in_collision when the goal's world holds the robot's spheres at that solution, or the load, deepest, and the message names what stands there as path_in_collision's does; self_collision when the seeds of the last IK attempt that reached the pose were stopped by the arm itself and not the world (up to goal_nearby.BLOCKING_SEEDS checked); no_clear_solution_found otherwise. It also says what would work. nearby is the smallest tilt of the approach that plans in the goal's own world, kept at the grip point between the fingertips: tilt_deg from goal_nearby.TILTS_DEG (10, 20, 30, 45) in TILT_DIRECTIONS (8) directions, 32 IK solves at most, and only a tilt with a joint solution is planned, one attempt each, at most NEARBY_PLANS (2) of them; nearby is null when none planned. other_arm_reaches says on a two-arm robot with an empty hand whether the other arm reaches the pose with nothing in the way, null otherwise. message joins all of it, the approach in world coordinates, and timing_s keeps the search as goal_diagnosis. The search is finite: it reports what it found, never that nothing exists. The start and goal checks use zero activation distance: a configuration is refused only when a sphere overlaps. Each IK query is solved in the world a plan to its pose would use, seeded from the start joints or a chained query's solution. The answer's detail keeps the start and goal check costs, the IK successes per planning attempt and, in ik_attempts, each attempt's seed population: the 32 seeds the solver's own result extraction ranked (the starting seeds when it exits early on them, populations_evaluated: 1, else the optimised ones), copied from that extraction without another solve. Rotation errors are V2's orientation metric (rotation_error_units: curobo_v2_orientation_metric).

Replay program

A sealed RoboTwin, LIBERO-Pro, RoboCasa365, RoboDojo or RoboLab run carries replay-program/, written by seal just before its inventory from evidence the run already holds, without a simulator (ora/environment/replay_program.py). program.json (ora.replay-program.v1) lists one step per agent action in order: controls runs the action's recorded controls (for a RoboTwin move stopped by a guard after its physics step, the prefix that ran; for RoboCasa365 one action vector per control step), hold steps the scene a recorded number of times with no new target (a RoboTwin wait), ticks feeds a RoboDojo action's recorded native ticks, skip is an action that moved nothing, and unreplayable marks a record the replay cannot reproduce (the program's status is then unreplayable and problems says why). Each step carries the receipt's end pose per arm (expect; on RoboCasa365 also base, the receipt's base_after, and state_before and state_after, the recorded hashes of the whole scene), and the program carries the verdict (expect: the official success and the first successful action for RoboTwin, the first terminating action for LIBERO-Pro and RoboLab, the first successful action and control step for RoboCasa365, the terminal state and native action count for RoboDojo), the task, seed, source commit and the record it was built from. program.py is the same steps as Python, one line per action (program.controls(3), program.hold(6, steps=120), ...). A run whose program cannot be written records replay-program/unavailable.json (ora.replay-program-unavailable.v1) and seals anyway; Synthetic and other backends get nothing.

RoboCasa365's record. native/controller-replay/ (ora.controller-replay-manifest.v2, backend robocasa, controller robocasa_composite_action) holds one entry per action: action-NNNN.npz with commands, float64 [control step, 13], each vector exactly as OmronIO.step sent it to robosuite's composite controller (arm, gripper, base, torso, mode), so the arm's paced path, the torso, the gripper and the move_base servo are all one thing to a replay; physics_steps counts control steps, 25 MuJoCo steps each; an action that sent none has no artifact and replayable: false. metadata.state_sha256.before and .after hash the scene's [time, qpos, qvel] as float64, objects and fixtures with the robot. region-order-round-NNNN.json (ora.robocasa-region-order.v1) keeps the order each counter listed its regions in while the round's kitchen was built, because the seed does not fix a kitchen (RoboCasa365 replay). Recording copies each vector before the step and writes after the action; it moves no random state and adds no simulator call, and the record is not policy-visible.

A RoboLab run records its controls under native/controller-replay/ in the layout of RoboTwin and LIBERO-Pro (manifest.json, events.jsonl, action-NNNN.npz; backend robolab, controller robolab_joint_targets; ora/environment/backends/robolab/control_record.py): for an action of T native actions, native_actions (T, 8) is the float32 tensor env.step received (flange position, quaternion wxyz, finger action) and joint_targets (T, 8, J) every joint's position target at each physics step as it entered PhysX, which is what the differential-IK term computed from the measured state, or a planned path's row. An action that moved nothing has no arrays; the reset's two held native actions are not recorded, since a replay runs the same reset. The record reaches no policy. A write that fails ends the record and leaves recording-failed.json beside it; the run goes on and seals with unavailable.json.

A RoboCasa365 or RoboLab run sealed before its record existed holds receipts only, a program is never rebuilt from them, and it stays without one: ora replay RUN --check OUT and --scene refuse it and --program DIR writes DIR/unavailable.json and exits 1.

ora replay RUN --check OUT (or python replay-program/program.py --check OUT) re-executes the program and writes OUT/replay-program-check.json (ora.replay-program-check.v1); nothing is written into the run. RoboTwin and LIBERO-Pro run in the plan's simulator interpreter through the Viewer replay's per-action code (ora/environment/replay_worker.py; job ora.replay-program-job.v1 and result ora.replay-program-result.v1 in replay_program_worker.py), with the caller's CUDA_VISIBLE_DEVICES taking precedence over the recording's; the check fails when any action's end pose differs from its receipt in any bit or the replay's verdict differs from the run's. RoboLab's clock starts at the state the policy first sees, after the reset's two held native actions, where its receipts' steps start: it has no execution capture, and its trace is on the receipts' clock. An Isaac body is a prim with an enabled rigid body, its pose read from one PhysX rigid-body view, or an instance the layout gives no rigid body (a table, a fixed collider, the room), posed once from USD; on RoboLab that is what the env root and the task scene draw with no rigid body under it, its poses are in the robot root's frame, and a body's cubes and cylinders are tessellated. The privileged-field audit of the trace (ora/agent/evidence/trace_privacy.py) refuses contact data, except a receipt's public contact detail: detail.contact_motion holding only the public contact and force fields (motion_feedback.py), where an observation carries the last action's effect and where a synchronous execution's ledger carries each action's receipt (execution.actions[].receipt, action_step_inventory[].actions[].receipt). Any other contact data under those keys still invalidates the run.

An argument name the run's own tool surface declares (a top-level inputSchema property of one of the plan's tool_surface.definitions) may hold a forbidden term, as a toolset's contact_speed_m_s does; it passes the audit only where it holds the policy's own argument (trace_privacy.declared_argument_names, policy_argument_values). That is a key with a value the policy wrote for that name in a tool call (the payload.arguments of any tool_call_proposed, a code-mode script's calls included, at any depth) or the default the surface declares for it, wherever that exact value appears: the call itself, the call in the provider request and response, and a tool result, receipt or later request that echoes it at whatever path the tool chose (numbers compare as numbers, so 3 and 3.0 are one value). The other is the name's declaration in a provider request's tool schema (tools[].function.parameters.properties or tools[].input_schema.properties at the root of a canonical or wire request artifact). The same key with any other value, in a tool result or anywhere else, is audited like any other key and invalidates the run, so declaring an argument cannot blind the audit to state a tool returns under its name (an arguments key in a tool result is no exception). A declared name that is exactly a forbidden term (contact, contacts, segmentation) is never exempt, and the values under an exempt key are still scanned.

In code mode the audit leaves out what a script wrote itself. In the result of the model's own bash call (run_python in a run sealed before that tool was retired) (the tool_result of a tool_call_proposed that names one of those tools and is not itself a script's call, payload.origin, in a plan with policy.code_mode, or policy.glue_code in plans made before the rename), it skips value, stdout, stderr, output (trace_privacy.SCRIPT_AUTHORED_FIELDS) and handed_back's reason and data (SCRIPT_HANDED_BACK_FIELDS). A script runs in a sandbox that sees no run, simulator or credential and reaches the world only through its calls: each is recorded as its own <call>#NNN event whose result is audited in full, an action's receipt as its environment_receipt, and an action that did not start returns only the harness's error message (action_not_started). So these fields hold the model's own computation over what its calls returned, under names the model chose: a point it hands back as contact is not contact sensing. The rest of that result (calls, actions_executed, action_limit, script_error, error_detail, any other handed_back key, the workspace listing), its payload with the execution ledger, the script's calls and every other event are audited as before; a plan without policy.code_mode (tool-call mode, free play) has no such result.

A later request repeats a script's result, so the audit reads it there the same way. In the requests of the model (REQUEST_KINDS) and of the context compactor (rollout_compactor_canonical_request, rollout_compactor_wire_request), and in the context packets whose compactor_messages the compactor's request repeats (lossless_context_semantic_packet, episode_context_capsule_packet; before 2026-11-04 the packets were read without it, and a script's handed-back p_contact refused a run's seal), the result of such a call, whether a role: tool message, an Anthropic tool_result block or the compactor packet's text block after its heading, is audited without those fields (trace_privacy.without_script_authored_messages); the SFT and wire exports scan it the same way, and export it unchanged. The exemption goes by the call and not by the field: every other tool's result under those names, and the rest of the request, stay audited.

The audit also leaves out the arguments the model wrote in its tool calls (2026-11-04). Privileged state reaches the policy only through what the harness shows it, which stays audited; a call's arguments are the model's own text, every key a name it chose, so a key holding a forbidden term is no evidence of a leak (a malformed write call whose one key held a whole module, with "pad contact" in a docstring, refused a run's seal). The provenance is exact (trace_privacy.reply_tool_arguments, model_tool_arguments): the reply that wrote the call (provider_response payload.message.tool_calls[].function.arguments); any later request or packet that repeats it as a tool call with the same id and the same arguments text (OpenAI function.arguments), or as an Anthropic tool_use block with that id whose input is what the text parses to; the proposal that parsed it (tool_call_proposed payload.arguments, equal to that parse); and, in code mode, the arguments a script the model called sent with its own calls (payload.origin of a script kind naming that script's call), which the gateway changes only by dropping nulls and making integral floats integers. A call the context rewrote (an aged or externalized arguments marker), a call no reply wrote and a proposal that differs from its reply are audited as before, and so is every tool result, receipt or request message that echoes an argument, the declared names of the rule above aside, and a tool schema that declares a forbidden name. The SFT and wire exports apply the same rule to the requests and replies they export. The agent core's own check (below) already skips the model's messages.

The agent core's own check of each provider request (causalMessageViolations, which ends a run with causal_context_forbidden_fields) reads a script's result the same way, for the same reason. Python sends it the script tools, only in code mode, with the two field lists (scriptTools, scriptAuthoredFields, scriptHandedBackFields in ora/agent/pi/domain.py). The compactor's check (compactorPrivateViolations) does not: the compactor reads the packet, so a reserved key such as contact or task_success refuses that compaction whoever wrote it.

Sandbox retention (save_sandbox)

sandbox/workspace is the execution model's working directory: its AGENTS.md, contract/ and the images handed to it (inputs/action-observations/, inputs/current-visual/, derived again after every action from the run's policy-observations/). In a long RoboDojo episode it holds over a gigabyte. The run option save_sandbox (RunSpec top level and task file; --set save_sandbox=false) chooses what is kept:

  • true (the default): every file stays, as before the option existed. The plan does not carry the key, so default plans keep their hashes. Keeping the sandbox by default, with false opt-in, is a recorded default-activation decision (user decision, 2026-10-30).
  • false: the plan records save_sandbox: false. The run is evaluated and sealed with its sandbox as usual (the seal inventory hashes every file); right after the landing seal (or ora seal) the files under sandbox/ are removed and sandbox/hashes.json (ora.sandbox-hashes.v1) lists each one's path, size and sha256 with the seal's inventory_sha256. A file that drifted before removal keeps the sandbox as it is and is recorded in native/sandbox-hashes.refusal.json.

Readers of a run without its sandbox: ora export archives every sealed file it still has plus sandbox/hashes.json (a removed file is accepted when the manifest lists it with the sealed sha256 and size); ora export-sft reads no sandbox file and proceeds; ora evaluate (and revalidation) refuse with the message that the sandbox files were not saved, and the evaluation.json written at seal time stands. Toolkit replay, the viewer and execution capture never read sandbox/. Execution capture is a separate option, runtime.execution_capture (enabled, 10 fps by default).

Evaluation validates source/action/trace/artifact boundaries before sealing. A seal binds the immutable inventory and final trace identity. The inventory (evaluate.inventory) refuses a symbolic link (the sandbox's reserved instruction aliases aside), a hard link, a non-regular file and a path named like a credential (CREDENTIAL_NAME_FRAGMENTS: credential, api-key, auth.json), except under native/code-workspace/ in a code-mode run outside free play (MODEL_NAMED_DIRECTORY, 2026-11-04): only the policy's write and edit calls and its commands write there, in a sandbox with a cleared environment that binds no run, home directory or credential store, so a name there is the model's and says nothing of the file (spots_auth.json held measured hole positions and refused a run's seal). In free play Pi's own shell runs on the host, and the rule applies there too. A failed seal is recorded as a refusal. Later revalidation writes separate reports without changing the original run. Synthetic's official_success remains null; only a benchmark's official boundary may supply a boolean.

Credentials and launch

Credential environment variables, TLS trust and simulator roots are local operator configuration. A provider key comes from its named environment variable first, then from the user-level ORA credential store (ora.agent.providers.user_store: pi-auth.json in $ORA_CONFIG_HOME, else $XDG_CONFIG_HOME/ora, else ~/.config/ora, mode 0600), which ora providers, the provider selector of ora interactive and ora play, and Pi's /login write; the ora entry point fills only variables the environment (or ora run's .env) leaves unset. User provider profiles for custom endpoints live in providers.yaml beside it, in the source-tracked catalog's schema (HTTPS or loopback HTTP), including the optional request_options and recovery_window_s that ora providers add --request-options/--recovery-window records under the catalog's own checks. provider_policy copies both into every policy it builds; a profile's recovery window also selects provider_recovery: first_token_deadline_v1, the recovery the window applies under as each attempt's first-token limit and the call's no-content window (the default baseline already names it; see provider recovery). A plan records the profile id and endpoint, never a key. Preflight checks configuration/qualification but never turns an installation into benchmark success evidence. ora doctor reports credential presence and setup discovery only, including the agent core's Node version and ora-pi package readiness (and, when none of ORA_API_KEY, OPENAI_API_KEY or ANTHROPIC_API_KEY is set, a line naming what ora run --env synthetic needs); it does not authenticate, render, initialize CUDA or qualify physics. The Pi core receives credentials through its process environment only; they never enter the provider spec it logs.

A bound compactor's key comes from its own profile's api_key_env by the same rule: the environment first, then the user credential store, which the ora entry point applies. Its base URL variable may be unset, in which case the binding's endpoint serves (as ora run defaults a profile's); a set value must equal that endpoint. A missing key or a different endpoint refuses the session, naming the variable or the endpoint, never the key. The Pi core receives the compactor's key in ORA_PI_COMPACTOR_API_KEY (a parent process's own value of that name never passes through), and the compactor's provider spec in InitParams without it. The environment worker is not handed the binding's base URL, key or proxy variables, as it is not handed the policy's. The key is never written to the plan, the events or the run directory.

ora run --env synthetic uses ORA_API_KEY (or the chosen provider's conventional key variable), ORA_BASE_URL, ORA_MODEL, ORA_PROVIDER, optional ORA_REASONING_EFFORT and ORA_SUPPORTS_IMAGES. Its default limits are explicit in quickstart.py and documented in the quickstart. With --provider-profile ID it takes that profile's policy instead (ora.app.quickstart.profile_policy, the provider_policy of every profile): its endpoint, model, key variable and limits. As on a GPU task, the profile's base-URL variable defaults to its endpoint and a missing key or another endpoint is refused before preflight; preflight then probes the provider as it does for any profile. The benchmark builders use their selected provider profiles instead.

ora launch RUN_SPEC requires exact preflight and confirmation; --yes is explicit non-interactive authorization for that plan. ora run --env synthetic starts only its bounded Synthetic plan. Retry cannot rewrite a sealed run or repeat an attempt that already dispatched a robot action.

Provider wire tool names

Strict providers reject dotted function names, so the OpenAI-compatible wire maps tool names reversibly (ora/agent/providers/tool_names.py, ported byte for byte in ora-pi/src/provider/tool_names.ts). A name outside ^[A-Za-z][A-Za-z0-9_-]{0,63}$ becomes a deterministic alias, its slug plus eight hex digits of its SHA-256 (robot.submit_action → robot_submit_action_<hash8>); definitions, a forced tool choice, assistant tool-call history and named tool results use the same map, including tools retained from an earlier phase, and responses return canonical names before their continuation state is bound. An alias collision fails closed. A returned tool name that is not a wire alias, not a name the request already carries and not strict (a provider tool-call parse defect, such as a parameter tag read as the function name) takes its alias before it enters the canonical history, so it never extends the disclosure below; the Runtime refuses it as tool_unavailable and the provider's raw events keep the name as sent. When any name is renamed, the mapping is disclosed to the model as a <wire_tool_aliases> JSON block appended, after a blank line, to the last leading system message (a text part for list content; the whole content when it is empty or null; a new index-0 system message only when the request has none). The wire never gains a second system message: Qwen3.x chat templates on vLLM and SGLang reject any system message after index 0 with HTTP 400. A leading system message whose content is not text is refused. The disclosure is byte-identical across the turns of one session, so the provider prefix stays cacheable. Surfaces that declare canonical_tool_names_v1 (the default LIBERO-Pro, RoboTwin and RoboDojo surfaces) advertise strict names and send no disclosure, so their wire bytes do not depend on this rule. Requests that carry dotted names (the Synthetic quickstart's robot_runtime_v2, frozen surfaces, custom tools) are affected: runs recorded before this layout sent the same disclosure text as a separate system message after the leading ones, so their archived wire requests differ from a rerun only in that message boundary. The Anthropic Messages projection sends the disclosure as its own system block and is unchanged.

Rejected tool replies

A provider reply whose tool calls cannot be dispatched as they stand is a recoverable reply that changes nothing in the world, on both wires (ora-pi/src/provider/openai.ts and anthropic.ts; the Python providers' ora/agent/providers/transport_failures.py and anthropic_reply.py, which the agent-core parity tests compare): its raw events stay in the evidence, every tool call of the reply leaves the canonical conversation, the model call counts, and the policy retries on the same observation after ORA's continuation (afterRejectedOutput, event provider_output_rejected). The output rejection records code, provider_stop_reason, rejected_tool_blocks (index, call id, tool name, the fragment's length and SHA-256, reason) and discarded_tool_block_count.

  • truncated_tool_call: the reply reached the output limit while it proposed tools; every call is rejected (provider_output_limit), complete or not.
  • invalid_tool_input_json: a complete reply in which any call's arguments do not decode to a JSON object (invalid_json, or not_an_object for an array, string or number); the whole batch is discarded with it.

ORA never guesses or repairs arguments. On the OpenAI-compatible wire the second case came on 2026-11-07: before, such a call (a Flash-Next bash call with empty arguments) stayed in the history and failed only at dispatch, and replaying its arguments made strict servers (SGLang) refuse every later request with HTTP 400 ("function.arguments must be valid JSON"), which ended the run as trusted_fault.

Path-only asset references

Composable policy assets name owned components by repository-relative path. policy.lock supplies their current bytes and content hashes; do not duplicate mutable owned-asset SHA literals inside a composable record. External source/model pins, reviewed evidence and generated compiled manifests retain their distinct identities. A reference escaping the tree, absent from the lock or using an inadmissible inline pin is refused. Regenerate compiled artifacts and the lock deliberately after changing their inputs.

A descriptor runs were sealed with keeps its bytes when a source it names moves: a source-only successor (a new descriptor file naming the new path, compiling the same card) becomes the binding for new runs, and ora/agent/composition/embodiment/moved_sources.py holds the one table (recorded path, sha256) -> path that answers for it now. A recorded path that is gone resolves to the new place only while the bytes there hash to the recorded sha256 (the provenance audit, load_public_geometry_binding, the jaw-centre re-hashes); an observation whose loaded-geometry verification names the predecessor's sha256 holds for the successor only while the predecessor still has those bytes and both bind the same robot geometry. Anything else is refused as before. The ARX X5 public-geometry descriptor v6 is v5 with the gripper module at ora/agent/toolkit/host/grasp/arx_x5_gripper.py; v5 stays for the RoboDojo runs sealed with it. The PandaOmron public-geometry descriptor v2 adds the arm mount, its reach admission and the wrist camera's mount to v1 (card facts, the same robot geometry; schema v2's optional topology.manipulators[].mount, geometry.reach_admission and sensing.cameras[].mount_in_controlled_frame, which a v1 descriptor refuses); v1 stays for the RoboCasa runs sealed with it and MOVED maps it to v2. The Franka Panda ...-session-split-v1-flat-surface-v1 descriptor cites the written-out LIBERO surface manifest for the workspace facts where its predecessor cited explicit_motion_v1/libero-definitions.json, which left the tree; the predecessor stays for the LIBERO runs sealed with it, and since nothing composes it, its source audit (which would refuse the missing file) never runs.

Storage admission floors

Synthetic defaults to 1 GiB free in the evidence workspace and 0.25 GiB in scratch. Isolated robot runtimes retain the 20 GiB workspace and 2 GiB scratch defaults. A host profile's explicit runtime_storage floors take precedence for either kind; capacity and writability are still probed. These are admission reserves, not predicted episode sizes.
