Robot-use agents can write code now

TL;DR.

  1. Code mode. We gave ORA's robot-use agent a new way to use the same harness. Each turn it can write and run a short program against the same tools, in a sandbox with a workspace that persists across the episode. With no exploration, demonstrations, task memory or robot training, DeepSeek-V4.1-Flash now solves 40% of RoboDojo, a benchmark of long, contact-rich bimanual tasks.
  2. Classical motion underneath. Every planned arm move now goes through one shared motion stack: a collision world built from the robot's own depth cameras, global path planning with cuRobo, checks that keep the wrist from unwinding, and timing that keeps each move within its speed caps. The agent decides what to do; the stack works out how the arm gets there.
  3. How agents behave with code. One tool per turn forces the agent to re-estimate, re-measure and re-check every turn. A program measures once, keeps the result, and checks its own work right after it moves. Given the sandbox, the agent builds its own tools: point clouds, pose builders and fitters that reappear in episode after episode.
  4. Three open models, two modes. On 40 RoboDojo tasks, DeepSeek, Qwen3.8-Flash-Next and Muse solve about as many tasks with code as with tool calls, but with code they need about half the robot decisions.

1. The major change: code mode

The same harness, exposed differently

ORA connects a language model to a robot through a harness:

  • a robot manual and a plain-language description of the task;
  • perception tools: segmentation, and metric 3D measurement from depth;
  • planning tools: grasp proposals and reachability;
  • motion tools: Cartesian moves, the gripper and the wrist;
  • a Supervisor that admits every motion one at a time and answers it with a receipt.

In October the agent used this harness the way most tool-using agents do. Each turn it called one tool, read the result, and decided what to do next.

Code mode keeps the harness and changes how the agent reaches it:

  • The same tools, as a library. Every tool the agent could call is importable from Python inside a sandbox, alongside a small library for frames, projections and depth point clouds.
  • A workspace that persists. The sandbox keeps a directory, /work, for the whole episode. A helper written in one turn can be imported in the next, and a measurement saved to a file can be read by every later program.
  • The same loop and the same authority. It is still turn by turn: one program is one decision, and the agent reads the program's output and the next observation before writing the next one. Every motion the program issues still goes to the Supervisor one at a time.

So the agent decides how much to do per turn. A program can compute on a point cloud without copying numbers through the model's reasoning. It can check reachability before moving and measure how far the arm missed after. It can branch on what it measures, and hand control back with a reason when a check fails. More freedom, the same guarantees.

40% on RoboDojo, zero-shot

RoboDojo is the hardest benchmark we run. Two ARX X5 arms work a tabletop: play a xylophone in order, thread nuts onto bolts, fold a cloth, insert tubes into a rack, build a tower from planks. Most tasks need dozens of motions, and each one depends on the geometry the earlier ones left behind.

With code mode and self-hosted DeepSeek-V4.1-Flash, ORA solves 80 of 198 cases (40.4%). That covers 40 tasks with five layouts each; two cases were invalid. Zero-shot here means:

  • no exploration: the agent never practises on a case or its layout before the scored episode;
  • no demonstrations and no task memory: nothing carries over from one case to another;
  • no robot training: the model is used as released, with no VLA policy underneath.

How we count successes is in Appendix A. ORA reads the arms' measured jaw opening, while RoboDojo's standard observation reports the commanded one. So these are ORA's numbers on RoboDojo's tasks. They are not leaderboard entries.

The same agent solves 79.6% of RoboTwin, 87.5% of LIBERO-Pro and 79.2% of RoboLab.

Against another agent with the same model. We ran Uni-Robot-Agent in its strongest setting with exactly our model and settings. On the 72 RoboDojo cases both systems finished, ORA solved 48.6% and Uni-Robot-Agent 36.1%, with 6.4 times fewer prompt tokens per success (24.6M vs 156.7M). Neither system can ask RoboDojo whether a task is complete. The cases both finished lean toward easier ones.

2. How traditional robotics helps agentic robots run smoothly

A language model is good at deciding what to do next: which object, which grasp, which order. It is a poor place to work out how an arm's joints get from here to there without touching the table. When a move goes wrong for a reason the model cannot see, the agent spends its next turns diagnosing a failure that was never its own.

In October, three things went wrong this way:

  • No collision world. On RoboDojo, a free move had no collision world to check against. On LIBERO, the planner knew only the robot itself, so a path through the table planned fine.
  • Wrist unwinding. A wrist could turn the long way round in the middle of a move and take a held object with it.
  • Hand-written timing. The timing that paced each move was hand-written, and on some moves it ran over its own speed cap.

One motion stack under every move

Since October we rebuilt how the arm moves, from standard robotics parts. The agent names the target and the kind of move. For every planned move, the stack then does five things:

  1. A collision world from depth. It builds a voxel world from the robot's own depth cameras. It removes the robot's own body, clears the space at the start and around the goal hand, and moves a held object from the world onto the hand. It uses no simulator state and no segmentation.
  2. A global path. cuRobo plans a collision-free path in that world. On the two-arm robots, the other arm is an obstacle in the same world.
  3. Wrist checks. When a plan would turn the wrist the long way round, the planner tries a straight joint line to the same pose and other arm solutions that turn the wrist less. With empty jaws, the stack can also use the jaw twin: the same grasp turned a half-turn about the approach axis, which a parallel gripper holds the same way. A gripper that may be holding something never flips. A path that still turns the hand more than 45 degrees beyond what the move asked for is refused before anything moves, with the reason.
  4. Timing. TOPP-RA finds the fastest progress along the path that keeps every joint and the hand within their speed and acceleration caps. Ruckig then checks the result against the joints' jerk bounds. Both arms of a two-arm move share one timeline, so they start and stop together.
  5. A dry run on request. Any moving action can be previewed before it runs: the planned path is drawn into the robot's own camera images, with the nearest object and its clearance. A move the planner refuses returns a picture of what was asked and the planner's reason.

The same stack serves RoboDojo, RoboTwin, LIBERO-Pro and RoboLab. A simulated backend adds only two things:

  • a description of its robot, which must match the simulator's own kinematics;
  • an adapter that sends the joint targets and reads the measured state back.

Moves the model marks as contact, such as a push, follow a straight line instead.

What it does not fix yet

  • Contact near the ends of a move. In one RoboDojo batch soon after the switch, 54 of 588 planned moves still moved an object by at least 5 mm. Most contact happens near the start or the goal, where the stack has to clear room for the hand. A light object barely slows the joints, so the arm's tracking cannot detect the touch either.
  • What the cameras cannot see. Unseen space counts as free, so an object hidden behind another is not in the world.
  • Wrist refusals. In the rollout behind the results above, 10–13% of runs hit at least one wrist refusal. The planner's own fixes (the straight joint line, other arm solutions, the jaw twin) landed after that rollout.

Both modes run on this stack, and programs lean on it most. A program may issue several moves before the model sees the scene again, so each move has to execute as planned, or come back refused with a reason the program can branch on.

3. How agents behave with tool calls and with code

To watch the two modes side by side, we ran a paired experiment on an earlier version of the harness: 20 RoboDojo tasks on three layouts, with the same model, the same tools and the same budgets (80 robot decisions, 200 model calls), and only the action mode changed.

What one turn delivers

Both modes think about equally long per model call. What differs is what a turn hands back:

  • a tool call is one call of about 180 characters, and 97% of tool-call turns that move the robot execute exactly one action;
  • a program is about 1.8k characters. It executes 3.6 actions on average, with the measurements and checks around them.

Where one tool per turn falls short

On the 15 cases only programs solved, the tool-call runs fail in four recurring ways. In the strips below, each box is one model turn.

1. What was measured gets estimated again. With tool calls, a measured quantity lives only in the model's text, and the next turn estimates it again. Playing a xylophone, the tool-call run:

  • revised its key map three times;
  • estimated the mallet's head offset at least six times;
  • restarted the sequence at least six times before it ran out of decisions;
  • on another layout, counted the keys as nine, then ten. There are eight.

The program run fitted all key boundaries once from the point cloud. It stored the measured mallet offset in a file that every later program read, and struck all eight keys in three programs.

2. Every measurement costs a turn. With tool calls, every geometry query and every computation takes a turn of its own. The compute tool accepts only literal expressions, so imports and comprehensions are refused. Inserting test tubes, the tool-call run probed the rack point by point for more than 20 turns, then set a tube between two holes, about 18 mm from the nearest centre. One program fitted circles to all ten holes in 0.76 seconds, without moving the robot.

3. The check comes a turn later, if at all. Fastening nuts, the tool-call run declared a nut "fully threaded" three times from the arm's position, released it, and watched it drop. The program measured the nut's depth below the bolt tip after every press, and pressed again while it still moved.

4. Every action costs a full turn of reasoning. A tool-call turn reasons about as long as a program turn, and then delivers one action. Ten of the 15 tool-call episodes ended with the model abandoning the task, several with most of the budget left. On these 15 cases, the tool-call runs made a median of 102 model calls, the programs 49.

More decisions do not close the gap

A program may issue up to 12 robot actions for one decision. On these 15 cases, programs ran 1,079 actions in 239 decisions, and tool calls 823 actions in 790 decisions. So is the gap just a bigger action budget? Two things say no.

First, most tool-call runs did not run out. Only 5 of the 15 ended at or near 80 decisions. The other 10 ended after 20 to 74 decisions:

  • 7 gave up;
  • 3 tripped the task's failure check on block-pushing tasks.

Second, we reran the 15 cases with tool calls only, at 300 decisions and 600 model calls (300 is about 80 times 3.6), with nothing else changed:

  • tool calls solved 3 of 15;
  • one of the three took only 27 decisions, inside the first budget, so it is run-to-run variation; only 2 needed more than 80 decisions (115 and 153);
  • none of the 12 failures used all 300: 9 gave up after 35 to 166 decisions, and 3 tripped the failure check.

The reasons the model gave for stopping match the four patterns:

  • It believed it was done. "Struck all seven xylophone keys in order", on a xylophone with eight keys. On arrange_largest_number, after 106 decisions: "Public completion contract appears fully satisfied".
  • It drew a wrong conclusion about the scene. On build_tower, layout 2: "no such board exists … the four tiers cannot be assembled". On layout 1: "no reachable pose can grip a 20 mm flat board". Programs built both towers on the same layouts.
  • It repeated the same failure. On fold_clothes, layout 1: "attempted roughly twenty grasps … Every close stalled at about 1.6 mm of fabric". Each retry moved to a new point without measuring why the last one failed.
  • It misread its budget. On fasten_screws, the run gave up at decision 54 with 246 decisions left. It read a remaining-budget field the wrong way round, which is the harness's to make plainer.

More decisions bought more attempts of the same kind.

What the sandbox changes

We expected programs to help because the model thinks a lot, and a tool call lets it act on only a sliver of that thinking. The data say something else:

  • within code mode, longer reasoning does not mean more actions: turns that reason for more than 40k characters average 0.86 robot actions, and turns of 2k to 10k characters about 1.8;
  • the longest-thinking turns produce programs that do not move the robot at all: fitting every hole of a rack, scanning reachable poses, comparing tile faces;
  • their results come back as numbers that later turns check and reuse.

Long thinking turns into measurement.

The workspace is what makes this pay off. Across all 59 program episodes:

  • the agent writes a median of 58 Python files per episode and reuses 7 of them in later turns;
  • in 73% of the turns that move the robot, the code that runs imports a module the agent wrote earlier in the same episode;
  • in the xylophone case, a scene.py written in turn 5 (a key table and a mallet-head finder) is imported by eight later files.

Each family points at something the harness should provide itself. The first two are now being added to the code-mode library. The functions an agent writes at runtime have become one of our main sources of harness improvements. TBD: link the library change when it lands.

Can a program cheat? A program can read files, so we checked what it read. The sandbox has no network and no view of the simulator, the run or any credential, and it cannot call the task checker. It can read ORA's own tool source and the robots' public geometry; simulator backends, task code and success checks are not mounted. Across the 59 episodes, programs in five cases searched that source for the task's name and found only developer comments. Reading the source happened in 7 of 20 solved cases and 19 of 39 failed ones.

Talk to it while it works

ORA's agent loop now runs on Pi, an open coding-agent core. So code mode also works in free play: load a scene with no task, type an instruction, and change your mind halfway.

The correction arrived while the agent was working. It read it before its next step, re-measured the magenta block, put blue back on it and green on top, and reported the measured height of each layer.

Different open models may suit different interfaces. We ran three of them on the current harness, on the same 40 RoboDojo tasks (one layout each), in both modes, with the same budgets:

Decisions, calls, tokens and reasoning (in tokens) are medians per episode; failed programs and refused calls are totals. A few cases per arm are missing because the simulator failed to start.

What the table says:

  • Success is close in both modes for all three models. On the current harness, tool calls have caught up with code on these tasks, unlike in the earlier paired experiment. We think part of the reason is that some of what programs did for themselves has since moved into the tools (grasp axes, wrist routing, clearer refusals); we have not tested that directly.
  • Code halves the robot decisions for every model. DeepSeek goes from 37 to 18, Qwen from 65 to 28, Muse from 58 to 34. Each decision does more.
  • The models use code differently.
    • DeepSeek writes long, careful programs: the most reasoning per call, the fewest failed programs, and 42% fewer prompt tokens per episode with code.
    • Qwen is the busiest. It makes the most calls in both modes, and its programs fail and get refused more often, so code costs it as many tokens as tool calls.
    • Muse reasons very little per call (a few hundred tokens), writes programs that fail often (864 over 38 episodes), and solves few tasks in either mode.
  • Cases solved by one mode only are few. DeepSeek: 3 with code only, 2 with tool calls only. Qwen: 5 and 5. Muse: 3 and 1.

Appendix A: how we count successes

RoboLab and RoboDojo each define a limit on simulator steps per episode. We do not stop the episode there. We record the benchmark's verdict at the limit as the official outcome and let the episode continue; a success reached later is a success after the limit. The numbers in this post count both. RoboTwin runs in its evaluation mode, where its own step limit ends the episode; our successes there use at most 21.5% of it (median 2.6%). LIBERO-Pro stops at its own horizon. So every success on those two is official.

Benchmark All successes Within the step limit
RoboLab 79.2% 67.0%
RoboDojo 40.4% 10.1%

Why we count successes after the limit. The step limits were set for learned policies that act at a fixed control rate. ORA is a turn-based agent: it measures, plans, moves and checks, and it spends simulator steps where a policy does not. Each ORA motion uses about twice the native steps of a direct joint command, and failed or retried motions add more. The late successes are real task completions by the benchmark's own check. They are not leaderboard numbers.

  • How late. The median late success lands at 1.57 times the limit on RoboDojo and 1.70 times on RoboLab.
  • Speed does not explain it. The default motion speed is already near the arms' joint limits on RoboDojo. Re-timing every move at the fastest preset would turn at most 10 of 60 (RoboDojo) and 3 of 61 (RoboLab) late successes into official ones. The steps go to extra decisions and stalled moves.
  • Comparisons in this post.
    • The paired experiment: of the 20 cases programs solved, 5 were within the limit; of the 6 cases tool calls solved, 2 were.
    • Against Uni-Robot-Agent: it reaches more successes within the limit than ORA (16 vs 9 of 72), because each ORA motion takes about twice the simulator steps.
    • The three-model table: within the limit, DeepSeek solves 8 cases in each mode, Qwen 7 with tool calls and 4 with code, and Muse 2 with tool calls and 4 with code.
