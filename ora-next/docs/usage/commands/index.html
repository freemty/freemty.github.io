Use ORA

Commands and what they write

ora is the generic operator surface for an already composed RunSpec and an indexed run. This page says what each command writes and when to use it. From a source checkout, use the repository wrapper:

./scripts/ora --help

The wrapper runs .venv/bin/python from the checkout when it exists, else $PYTHON, else python3. If your environment lives elsewhere (for example via UV_PROJECT_ENVIRONMENT), use uv run --locked ora ... or set PYTHON to that environment's interpreter. An installed wheel exposes the same command as ora. ora run --env, ora local and ora play select a task and seed and compose the RunSpec themselves; the per-environment composers (ora spec robotwin|libero|robodojo|robocasa|robolab, the tools each backend declares in ora/orchestrator/backends/registry.py) write one for the review and launch commands below. ora --help lists the commands in five groups (running an episode, formal runs and evidence, qualification and suites, configuration, developer); ora <command> --help gives one command's options, and the command reference, generated from the parser by ora dev cli-reference, prints all of them. ora help topics lists the short topic pages shipped with ORA. One internal command is deliberately excluded from the public command set and from ora --help: experiments, a development view of the experiment-identity registry. A launch's supervisor is its own process (python -m ora.orchestrator.supervise), which an operator never invokes.

ora --version prints ora <version>. Run from a source checkout (the repository's pyproject.toml beside the ora package), it is the version in that pyproject.toml, even when an older editable install's metadata says otherwise; from a wheel install, it is the installed ora-agent package's version (ora.version). The terminal transcript header shows the same version.

Normal lifecycle

Use the owning experiment CLI to compose the RunSpec, then follow the generic control lifecycle:

./scripts/ora plan validate path/to/run-spec.yaml
./scripts/ora plan show path/to/run-spec.yaml
./scripts/ora plan context path/to/run-spec.yaml
./scripts/ora plan preflight path/to/run-spec.yaml
./scripts/ora launch path/to/run-spec.yaml

./scripts/ora status RUN_ID
./scripts/ora watch RUN_ID
./scripts/ora metrics RUN_ID
./scripts/ora evaluate RUN_ID
./scripts/ora seal RUN_ID
./scripts/ora export RUN_ID

launch is the only command in that sequence that starts an episode. A preflight can still contact the configured provider and therefore may require explicit billable confirmation in the owning experiment CLI. Use stop only for the exact active run; do not replace it with a broad process kill.

For Native live-marker policies, plan preflight, launch and retry can probe the configured standby credential pool. HTTP 401, 402, 403 or 429 advances to the next distinct key, with at most one complete qualification attempt per candidate. Other errors stop admission. A successful launch pins the qualified credential in the child environment; reports contain indices, never secrets. launch and retry require their own fresh qualification, not a previously saved report. See configuration and evidence.

Remote GPU server: ora-remote

./scripts/ora-remote HOST [--repo PATH] [--local-port N] [--remote-port N] [--connect-timeout S] [--no-browser] [--new] [--web] {play,interactive,attach,watch,web} [ORA arguments ...] runs on your own computer. It runs that ora command on HOST over one ssh -tt connection that forwards one loopback port, shows the command's Pi terminal UI in this terminal (passing this terminal's image protocol as pi-tui settings) and opens the forwarded world view in a local browser once it answers. --web also opens ORA's web page for the run, and the web command opens only the page (the host needs ora web setup). The same play or interactive command attaches again to the run it left going (--new starts another). It never adds --confirm-launch, retries SSH or launches anything itself; see Using ORA on a remote GPU server.

What “tested” means

The locked pytest suite checks every public command name, their parser order, each command's one-line help and --help (in process, at the parser; one subprocess runs scripts/ora --help), their dispatch branch, the generated command reference, the topic pages and this table. It also tests the underlying deterministic RunSpec, context, preflight, workspace/index, policy-state, metrics, evaluation, sealing, archive and SFT contracts with fake or Synthetic boundaries.

Pytest does not launch a paid model or a live LIBERO/RoboTwin simulator. Consequently, launch, retry, watch and stop have deterministic dispatcher, parser and help coverage. Supervisor leases, run indexing and fake-process boundaries are tested separately, but the exact real host/process/environment path is qualified only by a source-bound experiment preflight or live qualification. Passing pytest means the CLI wiring and fail-closed contracts are intact; it is not evidence that a particular provider, host or robot task is currently qualified.

Environment tools

ora spec ENV, ora qualify ENV and ora play audit --env ENV hand the rest of the line to the tools the environment's backend declares (spec_tools, qualify_tools and play_audit in ora/orchestrator/backends/registry.py); ora spec ENV and ora qualify ENV list them, and each tool's --help gives its options. What they check and write is described with each environment:

  • RoboTwin evaluation seeds (ora qualify robotwin) and the play-scene audit (ora play audit --env robotwin): RoboTwin seed and scene qualification.
  • The RoboTwin and LIBERO RunSpec builders (ora spec robotwin|libero): fresh benchmark specifications.
  • The RoboDojo lane, physics probe and motion qualification (ora qualify robodojo): RoboDojo and RoboDojo motion qualification.
  • RoboCasa365 and RoboLab (ora spec robocasa|robolab, ora qualify robocasa|robolab motion): RoboCasa365 and RoboLab backends.

Generic command maintenance

When adding, renaming or removing a public command, update all of the following in the same change:

  1. the command's module in ora/app/ (register and run), and its entries in COMMANDS and GROUPS in ora/app/main.py (the public commands are the commands GROUPS lists, in its order);
  2. the command table above;
  3. the generated command reference: run ./scripts/ora dev cli-reference --write (tests/ora/app/test_cli_reference.py fails on a stale page);
  4. the command's deterministic contract or dispatcher test;
  5. any topic page in ora/app/help/ that shows the command (tests/ora/app/test_help.py fails on a page naming a command that does not exist); and
  6. scripts/README.md when the operator workflow changes.

A new environment's spec, qualify and play-audit tools need no app change: its backend declares them (spec_tools, qualify_tools, play_audit in ora/orchestrator/backends/registry.py) and ora spec|qualify ENV and ora play audit --env ENV find them. Regenerate the command reference, whose tables list them.

Do not add another shell wrapper merely to fill in a task, config or milestone. Those selections belong to the explicit experiment CLI so the chosen study identity remains visible.

Startup binding and refusal diagnostics

Generic launch and preflight share the controller-source check with the RoboTwin factory and select resident endpoints from the same RunPlan bindings as policy tools. Missing experiment-wrapper environment setup no longer redirects a bound SAM3/grasp client to a default port. Conflicting explicit endpoint overrides still fail identity validation. A duplicate single-attempt claim prints its cohort/cell, original run/plan and creation time to stderr and returns a failure exit code; missing historical owner metadata is explicitly unavailable.

ora services --help lists the resident-service commands (start, status, stop, qualify); examples/official_suite/run.py --help lists the official-suite cell, compose and queue commands.
