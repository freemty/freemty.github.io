Use ORA

Viewer, LIBERO Atlas and RoboTwin Gallery

The registry is a local, read-only Flask application for Runtime evidence, experiment task sheets, the pinned LIBERO/LIBERO-Pro atlas, and the pinned RoboTwin task catalog. ORA also uses a small exact-run world-view service for live execution capture. Neither service writes run artifacts or contacts a simulator.

For original capture, diagnostic reconstruction, cache verification and new backend integration, use the shared trajectory-to-Viewer procedure. Reuse the listed modules instead of adding a per-experiment video pipeline.

Shared frontend template

Every page uses the same minimal light shell: system fonts, compact controls, thin borders and unfiltered media. Open /style-guide for a small example. viewer/templates/base.html and viewer/static/base.css own the reusable shell and defaults; viewer/static/viewer.css owns component layout. See the frontend style guide before adding a page. The installed package includes these HTML and CSS assets.

ORA live world view

ora/orchestrator/world_view.py (in ora, not this package) supplies ORA's loopback-only companion window. A human terminal running ora interactive opens it in a waiting state before task selection; a live ora watch RUN binds it to that exact run. The service follows original execution-capture PNG frames and the complete prefix of the append-only capture timeline. It takes no Runtime lease and starts no model or simulator. Browser acknowledgements affect only its ephemeral connection state, not run evidence or official outcomes.

The view distinguishes waiting, holding, executing, capture-behind, error and disconnected states. A connection becomes confirmed only after the browser decodes and acknowledges an image for the bound run. A last captured frame can remain on screen while capture catches up; the status preserves that distinction. A sealed transcript replay does not automatically open this live view because its replay clock differs from the latest captured frame.

The CLI defaults to --world-view auto --world-port 0 --world-browser auto for human sessions. --world-view off selects terminal-only use; --world-browser off leaves the service available without browser launch. JSON-lines clients are headless unless they explicitly request a world port or public URL. For a remote simulation host, scripts/ora-remote provides the loopback tunnel and opens the browser on the operator's local computer. Local execution remains subject to the supplied task's host and simulator qualifications; a full Mac CPU/MuJoCo preset is not yet qualified. See the run guide and public interfaces.

Start the viewer

From the repository root:

uv run --locked ora-viewer --open-browser
uv run --locked ora-viewer --open-browser --page libero

ora-viewer is the Viewer's console script (viewer/app.py); uv run --locked runs it from the locked environment. It starts the Viewer at http://127.0.0.1:5012 and, with --open-browser, opens the default browser. Stop it with Ctrl-C. ora-viewer compile videos|previews builds the Viewer's videos and the LIBERO gallery previews offline, outside the web process. ora-viewer dashboard serves the separate run dashboard. The default runs page is the evidence registry. --page libero opens the integrated LIBERO/LIBERO-Pro atlas directly (libero-pro remains an alias); --page robotwin opens the RoboTwin catalog. These are allowlisted start pages for the same read-only process, not separate Viewer implementations.

The default page is also the global experiment index: evidence class, backend, experiment ID, task, seed, lifecycle state and official outcome are composable filters. Backend names are rendered as RoboTwin and LIBERO/LIBERO-Pro rather than leaking only adapter identifiers. An experiment name links to this registry filtered to that experiment (/?view=all&experiment=ID); there is no separate experiment page or registry.

Opening the field guide never starts LIBERO or MuJoCo. It reads the current preview manifest and shows explicit placeholders when images are unavailable. Check or build the independently generated seed-0 preview cache with:

uv run --locked ora-viewer compile previews --status
uv run --locked ora-viewer compile previews  # only on the pinned LIBERO-Pro host

To start without opening a browser, use:

uv run --locked python viewer/app.py

Both launch forms accept --host, --port and --page. The default bind is intentionally local-only; change it only when the surrounding network boundary is controlled. --page only selects the browser URL and does not change which read-only routes the server exposes.

The shared outputs/ root is discovered automatically from Git's common checkout, so starting the Viewer from any linked worktree shows the same new runs. It also discovers live linked-worktree output roots and recursively reads legacy worktree-snapshots collections. Use ORA_WORKSPACE_ROOT=/absolute/path to place both shared outputs/ and .harness-runtime/ outside the primary checkout; use the same value for every launcher and Viewer process on that machine.

To inspect copied output collections in addition to automatic discovery, set the path-separated ORA_EXTRA_OUTPUT_ROOTS. To replace automatic discovery with an explicit collection or experiment workspace, repeat --outputs-root as needed:

uv run --locked python viewer/app.py \
  --outputs-root /path/to/outputs \
  --outputs-root /path/to/another-experiment-workspace

The Viewer recognizes a run only as a directory with a plan.json whose parent directory is named runs, so each target must be one of:

  • an outputs root, holding <experiment>/runs/<run_id>/ (at any depth);
  • one experiment's directory, holding runs/<run_id>/;
  • one run directory, .../<experiment>/runs/<run_id>.

The runs/ directory itself is not a target, and neither is a run copied outside a runs/ directory (copies/<run_id>/ is never found: /run/<run_id> answers 404). Copy a run as <dir>/<experiment>/runs/<run_id>/ and pass <dir>. Run IDs must remain unique across all configured roots. The Viewer header shows the shared evidence destination and every active discovery root.

The Viewer is not strictly read-only on its roots: opening a run's video, trajectory or replay writes derived caches into the run's experiment directory, <experiment>/viewer-derived/<run_id>/, beside runs/ (never into the run). Point --outputs-root at a copy rather than at a shared outputs root that others own and that you mean only to read.

The run index and cost list read registration metadata without projecting full trajectories to inspect video caches. The index labels video availability check in run; opening an exact run checks its source-bound media. An omitted cache check is not displayed as a missing video. For discovery and subsequent registration reuse, the recursive run-root scan is reused for five seconds after completion per configured root set, and each run's registration is reused while an evidence fingerprint — the exact stat identity of its plan/status/result/launch/evaluation/seal/event files plus the derived-video directory listing — is unchanged. A newly landed or re-derived run therefore appears within one refresh without re-reading every sealed run on every filter click.

Run dashboard

ora-viewer dashboard serves a second read-only page over ORA run directories, separate from the Viewer above: a run browser for cohorts of runs and the conditions they compare, and a 3D replay of runs of every backend. It is ported from Shaoxiong Duan's code-vs-tools dashboard (snapshot 2026-10-31) and lives in viewer/dashboard/: a standard-library HTTP server (server.py, run parsing in runs.py and agent.py, the replay bundle in replay.py for RoboDojo and replay_receipts.py for the other backends, robot descriptions in robots.py, object meshes in meshes.py, scene traces in scene_trace.py) and plain JavaScript pages (static/) on the shared light template.

uv run --locked ora-viewer dashboard --outputs /path/to/outputs --experiment NAME
Option Meaning
--outputs ROOT An outputs root holding <experiment>/runs/<run_id>/, or one experiment directory holding runs/
--experiment NAME Show only this experiment (default: every experiment under the root)
--condition PLAN_PATH Label each run by the value at this dotted plan path, for example policy.tool_surface.profile or policy.baseline.id; default: code when the plan has policy.code_mode, else tools
--hide-cohorts REGEX Cohorts whose name matches stay out of the overview, its recent runs and "all cohorts", with a switch there to show them. Their own pages still open, and nothing is deleted
--host, --port Bind address (default 127.0.0.1, local only) and port (default 5013)
--robodojo-assets DIR RoboDojo's Assets directory for the 3D replay: the X5 URDF under Robots/x5, object assets under Object/; default $ROBODOJO_ASSET_ROOT
--robotwin-root DIR A RoboTwin checkout for the 3D replay's aloha-agilex robot (assets/embodiments/aloha-agilex: its config.yml and URDF); default $ROBOTWIN_ROOT
--scene-traces DIR A directory of scene traces (DIR/<run_id>/, as ora replay RUN --scene --scene-traces DIR writes them); default: scene-trace/ beside each run's runs/ directory
--mesh-python PATH An interpreter with usd-core for the object meshes (default: the dashboard's own interpreter)
--cache DIR Derived point clouds and meshes (default $XDG_CACHE_HOME/ora/dashboard, else ~/.cache/ora/dashboard)

What it shows:

  • Overview: every experiment's runs together ("all cohorts") and each cohort, with progress, states and successes by condition, then the most recent runs. A run's cohort is its plan's launch_admission.cohort_id, else the plan's config without the task and what follows it, else the experiment. Launches usually make one cohort per treatment, so conditions meet in an experiment's "all cohorts" view.

  • Cohort: a task x seed matrix (task x layout for RoboDojo) with one square per condition (the latest run of the cell; lettered, with a legend, and marked success, fail, running or fault), a per-task table of successes, median wall time, model calls and native actions per condition (each played round of a multi-round session counts), and a filterable table of the runs.

  • Run: the verdict, termination, condition, backend, task and seed, host and card (from launch.json), wall time, calls, tokens and raw-file links; the Timeline of each observation step (every camera the backend recorded, model calls with their reasoning, tool calls with a code-mode script's own calls under the call that ran it, receipts); for code-mode runs Agent's files, every version of every file the agent wrote, from the workspace snapshots (native/code-workspace-objects/); Logs and Run events. The compare page puts two runs side by side.

  • 3D replay of one round of a run on one clock: a strip of every robot command (native/receipts/) coloured by interaction mode where the receipt has one, else by action, failures hatched; end-effector paths; the agent's RGB-D at the latest observation as a point cloud; the camera frames; and the agent's trace (reasoning, code or tool arguments, results, the exact images it was shown) placed at the commands each call caused, a skill sequence at all its stages. The clock and what the robot layer shows differ by backend:

    Backend Clock Robot Paths Cameras
    RoboDojo native actions (25 Hz) dual ARX X5 posed per native action from native/controller/; FK check vs logged ee_link per native action execution capture
    RoboTwin SAPIEN steps (250 Hz) of the execution capture aloha-agilex posed per SAPIEN step from native/controller-replay/*.npz (measured arm joints; fingers from the measured opening and each set_gripper's commanded ramp); FK check vs measured TCP per SAPIEN step execution capture
    LIBERO-Pro MuJoCo steps (500 Hz) of the execution capture none (its controller replay records commands only) each command's measured start and end, each observation execution capture
    RoboCasa365 native actions, each receipt's steps_used accumulated (rate not recorded) the scene trace's links, when the run has one (end effector and base only otherwise) as LIBERO-Pro, plus the mobile base's path and pose observation frames held
    RoboLab native actions (15 Hz), as RoboCasa365 the scene trace's links, when the run has one (end effector only otherwise) as LIBERO-Pro, per native action with a trace observation frames held

    An observation sits at the end of the command its observation.json names (previous_execution_receipt; RoboDojo: native/observation-clocks.jsonl). The toolbar names the clock's unit and rate, and for a posed robot the distance between the URDF's forward kinematics of the logged joints and the logged pose, which reads 0.0 mm when the mounts and joint mapping are right. Point clouds are cropped to RoboDojo's workspace, elsewhere to the box of the run's end-effector positions grown by 0.6 m (0.4 m above). A Synthetic run has no 3D replay (api/replay answers 422).

    Scene objects are developer-only and never shown to the agent. RoboDojo runs launched with ground-truth capture (<experiment>/ground-truth/<run_id>/) draw them at their simulator poses. A RoboTwin, LIBERO-Pro, RoboCasa365 or RoboLab run, and a RoboDojo run with no ground truth, draws them from its scene trace, which ora replay RUN --scene recovers from a sealed run's replay program: it re-executes the run as --check does, on a simulator lane of its own (RoboDojo: --resource-profile), and keeps the trace only when the check passes, so the dashboard never starts a simulator and a run that diverges gets none. A RoboCasa365 or RoboLab run sealed before it recorded its per-tick controls has no program, and its objects layer says so. The trace (<experiment>/scene-trace/<run_id>/, format in ora/environment/scene_trace.py) holds every body's pose on the execution capture's clock, or the receipts' on RoboCasa365 and RoboLab (about 50 Hz on RoboTwin and LIBERO-Pro, every fifth SAPIEN step and every tenth MuJoCo step, every native action on RoboDojo, 25 Hz, RoboCasa365, 20 Hz, 25 MuJoCo steps to the native action, and RoboLab, 15 Hz, plus each action's last step; between rows the page interpolates) and each body's visual mesh. The objects layer draws the task's objects and clutter, and the table goes under the table toggle with any other fixed body (RoboDojo's camera stand, which stands in front of the default view). The wall, the ground and RoboDojo's room are in the trace but not drawn, they would stand between the camera and the scene; a kitchen's walls and floors likewise, while its counters stay, and its doors and drawers are objects, since they move. A RoboDojo trace also gives a run without ground truth its rounds and each command's span. Without a trace the toggle is disabled and says which command makes one, or that the run recorded no controls to replay.

    The robot comes from the trace where the bundle has no URDF for it, which is LIBERO-Pro and RoboCasa365 always (the Omron base is links like the arm's, so the trace poses it) and RoboTwin or RoboDojo without --robotwin-root or --robodojo-assets: its links are bodies of kind robot, drawn under the robot toggle, with no label and not in the Objects table, and the "no robot model" note goes. Where the URDF is posed the links stay undrawn. A MuJoCo trace also names the TCP, so the end-effector path and marker follow the hand between commands instead of joining the receipts' end poses.

Runs of RoboDojo, RoboTwin, LIBERO-Pro, RoboCasa365 and RoboLab all open in the run browser; a file a backend does not write (execution capture for RoboCasa365 and RoboLab, native/controller/ outside RoboDojo) is simply absent.

The dashboard is read-only. It never writes to a run or to the outputs root; derived point clouds and meshes go to --cache. api/file and api/ls read only inside the outputs root, after resolving links (403 elsewhere); api/scene-trace only a trace's poses.bin and meshes/<id>.glb, inside that run's trace directory, after resolving links (404 elsewhere); a robot description's files (robot/x5/..., robot/aloha/...) only inside its directory, and visual meshes over 8 MB (decorative cameras and cart bodies) are listed in the bundle so the page never requests them (the aloha-agilex's two rear master arms, never commanded and at their URDF pose, therefore appear without the cart that carries them); every request other than GET or HEAD is refused. Parsed files are cached by (path, mtime, size), append-only jsonl files are read incrementally, the scan of all runs is reused for five seconds, large JSON responses are gzip-compressed, and every URL is relative, so the page also works behind a proxy at a sub-path.

The run browser needs only the standard library. The 3D replay's point clouds and RoboTwin's controller replay need numpy (and Pillow for the clouds; both in ORA's environment), its object meshes usd-core in --mesh-python, and the browser loads three.js 0.160.0 and urdf-loader 0.12.6 from cdn.jsdelivr.net. Not ported from the original: its round-manager input, cluster resource panel, design-review page and feedback endpoint, and its code-policy tab, which read conventions of the code-vs-tools workspace.

Round Results and Process Videos

The LIBERO task-cohort page shows a round matrix automatically when its visible runs contain session rounds. Each row identifies one exact run, task, seed, config and source. Cells distinguish official success/failure, running, incomplete, unscored and unrun rounds. The summary reports scored and completed counts plus the first recorded success; persistent rounds retain their session relationship and do not become independent Pass@K trials. The task-cohort page selects RunPlan identities before registering traces from the selected scope. It omits expensive video-availability inspection, which is represented as uninspected and cached separately from full registry rows. Opening a video still performs media verification.

The Episode Notebook opens with an Execution / Full process player. Choose a round or a recorded chapter to seek the video; playback highlights its ActionStep, and the Notebook outline seeks back to that step. Switching video versions preserves the event/action position. A round can play within a cached full video and stops at its boundary. Export full MP4 labels that fallback; a separate round export requires its own offline compile.

Full process follows recorded observations, model responses, grounding/grasp results, execution clips, receipts and official round outcomes. Native tool_image artifacts are hash-verified, including older segmentation returns. Repeated calls retain their identities and recorded order. Managed summaries declare incomplete ordering. The inspector links to original events and shows complete recorded reasoning in a collapsed panel. Reasoning excerpts and Context select additional video content; they never reconstruct unrecorded model reasoning.

Compile an optional version explicitly, using an exact discovered run ID:

uv run --locked ora-viewer compile videos --run-id RUN_ID --video-mode process
uv run --locked ora-viewer compile videos --run-id RUN_ID --video-mode process \
  --round 2 --include-reasoning --include-context
uv run --locked ora-viewer compile videos --run-id RUN_ID --video-mode execution --round 2

--round is one-based. Omit it for all recorded rounds; --run-id may repeat and selects exact runs independently of the default batch evidence filter. Exact IDs are resolved before trace registration; duplicate IDs across output roots are rejected. --card-seconds accepts 0.5–15 seconds (default 2.5); observation and receipt cards have shorter caps. Text uses labelled excerpts and images paginate in groups of four. The web player uses the default card duration. The existing --replay-mode review|forensic selects execution sampling independently of --video-mode execution|process.

Process compilation uses CPU-only Pillow/FFmpeg and verified existing MP4 plus timeline pairs. It does not launch a simulator, provider or perception service. Without compatible execution media, it makes a labelled observation-boundary presentation. Exact execution compiles retain the existing offline replay prerequisites. The web process only serves presentation caches and returns a compile command when a selected version is missing. Generated MP4s and chapter manifests stay under viewer-derived, outside the sealed run and Git. Reading time is edited presentation time, with recorded latency preserved separately.

Trajectory compilation

The Viewer does not require an experiment-specific renderer. Every indexed run is compiled at read time from the common evidence surface:

flowchart LR
  P[RunPlan] --> C[Read-only trajectory compiler]
  E[events.jsonl] --> C
  S[policy-state chain] --> C
  A[agent transcript] --> C
  R[result / evaluation / seal] --> C
  X[optional same-session frames] --> C
  T[default compact controller trace] --> W[isolated same-source/seed simulator replay]
  W --> C
  C --> B[viewer-trajectory.v1]
  B --> V[Episode Notebook]
  B --> J[JSON API]

The compiler prefers outer causal events and falls back to adjacent immutable policy-state records for older or small Synthetic runs. It verifies that every rendered image path remains inside the resolved run root, records source hashes, and never writes a cache or derived file into the run. A sealed run therefore remains byte-for-byte unchanged when viewed.

RoboTwin and LIBERO/LIBERO-Pro share one media-source rule. The live simulator records the numeric commands that actually crossed its controller boundary, not thousands of rendered images: complete dense arm/gripper paths for RoboTwin and issued OSC or JOINT_POSITION commands for LIBERO. When no explicit same-session execution timeline exists, the Viewer starts the exact external simulator binding in an isolated worker, resets the recorded task/seed and applies those commands without running the policy, perception tools, planner or official evaluator. It captures all registered review cameras after replayed physics steps. These frames are useful near-deterministic debugging media, but remain viewer_derived_controller_replay, never actual original execution evidence. A run recorded without a controller trace stays on the explicitly labelled action-boundary fallback. Missing source, Runtime or simulator bindings remain operator-visible compilation errors.

RoboTwin control profile v4 uses the same replay contract for validated global paths and local Cartesian DLS: the manifest contains the actual issued joint position/velocity sequence, not a request that re-invokes CuRobo or recomputes a Jacobian. Separate robotwin-plan-artifact.v1 and local-Cartesian artifacts let the evidence panes compare planned FK, issued targets and measured TCP. Payload manifests contain only compact public-RGB-D numeric geometry and hashes; the Viewer never upgrades their planning-assumption boundary to attachment truth.

Same-session RoboTwin timeline entries may use paths relative to the run root or, as emitted by the isolated backend, relative to native/. The reader normalizes both forms, then applies the same containment check; it never accepts an absolute path or traversal outside the run. Motion-receipt events likewise may carry the immutable {path, sha256, receipt} artifact wrapper. Viewer status/residual projection unwraps only the nested receipt, while the raw trajectory keeps the original wrapper and hashes visible.

For a result carrying explicit session and rounds evidence, the compiler adds ora.viewer-session-rounds.v1. It maps each recorded policy_state_steps.start/end_exclusive interval onto round-local ActionStep identities and preserves decisions, refused proposals, model calls, simulator steps, duration and the environment-owned Boolean for each round. Decisions count accepted world mutations only; a certified zero-write refusal is carried as refused_proposals (null on runs recorded before the counter), shown in the round matrix as N actions, M refused and in the run summary. The projection records one persistent AgentSession and reset EnvironmentSessions as different continuity axes. Its aggregate official_success remains null: 5/5 rounds, success-within-5 and standard Pass@5 are not interchangeable claims. A run or round with success_after_official_limit reads as a success after the official limit everywhere a verdict shows, with its own outcome filter: its official_success is false, it counts in no success total, and it is no failure.

The raw trajectory viewer uses a separate lossless index. It scans events.jsonl, agent-events.jsonl and agent-transcript.jsonl, retaining each stream's source path, one-based line number, byte-derived line hash and original order. A recorded timestamp merge makes cross-stream navigation practical, but is never represented as canonical causality. The browser receives only compact metadata and searchable visible text for the event rail; selecting an event loads its exact JSONL line from the per-event endpoint. This keeps large provider requests and responses out of the initial page while making the unaltered payload inspectable and copyable.

For reviewed experiment runs, the compiler may load one tracked experiments/<experiment>/viewer-analysis.json. It accepts the overlay only when its schema, exact run ID and full RunPlan source commit all match. Multiple matches fail closed. The file can name findings, incidents and recorded state steps, but cannot modify event payloads, add run artifacts or override any official verdict. Its tracked source path and curated_navigation_only status are exposed in the trajectory API and on the page.

Observation-cycle synchronization is also read-only. Runtime observation records and Agent observation_step evidence bind events to the same compiled actual camera groups used by the Episode Notebook. Current/next images, action and receipt summaries in the right pane are navigation aids, not substitutes for the selected raw record. The original run files remain the authority.

Historical compatibility is evidence-driven. Pre-policy-state runs recover their exact images from policy-observations/<observation-id>/ and map Agent transcripts by recorded turn order. Native runs map provider responses from the canonical agent-events.jsonl. Operator-world frames are labelled control_only; they are never presented as policy-visible input.

Text-grounding overlays are recovered only through their recorded grounding_query_materialized reference and SHA-256. A missing, malformed or hash-mismatched overlay is omitted rather than inferred. This lets a reviewer compare the exact policy-visible target selection with a later grasp-plan preview without changing either causal event. Grounding v2 events additionally bind one independently hashed candidate card per returned T0/T1/T2 target. The Viewer places those exact policy-visible cards after the overview and omits only a missing or mismatched card; it never rebuilds or sharpens an alternative crop. Historical v1 events remain single-overlay. The tool handlers log these events, and so does a toolkit surface whose environment plans its moves (docs/reference/toolkit-execution.md). RoboDojo's toolkit surfaces do not log them for vision_ground, grasp_plan or mark_point, so those calls add no derived image to a RoboDojo step.

Episode Notebook review model

The default run page treats an episode as one continuous review document rather than a slideshow with one selected step. This follows the useful reading hierarchy in CapX-style execution viewers—model response followed by execution details—and the earlier Agent-as-Policy viewer's sticky episode outline, while keeping ORA evidence identities and privilege labels authoritative. It does not reproduce another system's chat UI or execution semantics.

Each compiled ActionStep is rendered in the same order:

  1. Current observation and visual artifacts. Large images appear first and carry their recorded policy_visible, control_only, or unrecorded visibility status. Clicking an image opens the exact contained artifact. A grasp_plan_materialized event adds both the hash-verified policy-visible target-local candidate contact sheet and the separately labelled review-only global point-cloud preview, each with candidate count. The exact input NPZ remains linked in raw event evidence. New events carry explicit artifact paths; earlier hash-only events resolve only the canonical grasp_query_ref policy overlay and are omitted on any hash mismatch.
  2. Recorded model response. Public assistant messages remain expanded. API-visible reasoning is explicitly labelled and collapsed; the Viewer does not reconstruct absent reasoning or expose private model state.
  3. Execution details. Policy-visible tool returns retain their order, then the Runtime action and Environment receipt appear as a pair. Short recorded fields support scanning; the projected payload remains expandable.
  4. Consequence. Post-action images are collapsed because they normally recur as the next ActionStep's current observation. This removes visual duplication without dropping the recorded artifact.

The left outline is derived from recorded action/tool names and follows the visible ActionStep while scrolling. J and K move between steps; global expand/collapse controls switch between close reading and rapid scanning. These interactions select or reveal existing evidence only. They do not create an episode summary, label a recovery, or infer whether an object was recognized, grasped, retained or correctly placed.

When result.json contains persistent-session round records, the notebook projects the exact policy-state ranges, per-round decisions/model calls and per-round official verdicts before the step feed. The session-level verdict is not synthesized from those cards. A matching curated analysis can separately name a recovery or bottleneck; its boundary statement remains visible beside the findings and every step link resolves to recorded evidence.

The embedded MP4 defaults to original run images: same-session execution frames when recorded, otherwise original observations at 1.4 seconds per snapshot. The player and video explicitly state that intervening motion was not recorded. Snapshot side panels distinguish the action after the displayed observation from the receipt after that action. No missing motion is inferred. This rule applies to every Runtime backend; catalog demonstration media remain separate attributed sources.

?replay_mode=forensic or --replay-mode forensic explicitly requests a simulator reconstruction for diagnosis. It executes the complete recorded target stream and all settle steps, sampling only camera frames. The former RoboTwin target-skipping shortcut has been removed. Every reconstructed frame warns that it may differ from the original run; accompanying original receipts are never presented as replay measurements. Pose endpoint agreement does not prove object/grasp fidelity, and reconstructed images do not adjudicate the original official verdict.

The cache lives under outputs/<experiment>/viewer-derived/<run_id>/ outside the run. The new source-selection contract, renderer hash and source image hashes enter its identity, invalidating older approximate default videos. Builders use per-output locks and share the completed immutable cache. visual_fidelity distinguishes original_frames_only from unverified_simulator_reconstruction. Fresh RoboTwin and LIBERO/LIBERO-Pro plans enable the shared bounded recorder. Finalized source frames bind round/action/simulation time and hashes; incomplete recordings and held-frame ages are visible. Finalized capture can be rendered for scripted qualification even when it has no policy observation steps; it does not create policy records or verdicts. Native control-action IDs remain distinct from policy-level notebook actions, including skill sub-actions without a matching receipt row.

For dense-target RoboTwin traces the isolated replay worker bypasses CuRobo construction entirely: it still verifies and initializes the pinned simulator, robot and cameras, but no planner is needed to apply already-recorded controller targets. Legacy EE-only traces retain normal planner initialization.

Compile every current formal run before review with:

uv run --locked ora-viewer compile videos

Use uv run --locked ora-viewer compile videos --video-scope libero to compile only formal LIBERO-Pro runs, or --video-scope robotwin to compile locally indexed formal, behavioral-attempt and diagnostic RoboTwin runs. Combine any command with repeatable --outputs-root; use --replay-mode forensic only for an explicit controller-step investigation. ora-viewer compile videos calls the same compiler as the web route; it contains no second rendering path. A controller replay needs the exact external simulator roots, Python binding, pinned revision and GPU resource from the recorded RunPlan. The RoboTwin recorded-trace producer and the controller-profile stack it re-executes ship with the same release as this Viewer, so the complete replay chain is live; a run recorded without a controller trace still fails closed with an explicit error instead of an empty video. Compile in batches only while that source-bound simulator slot is free. Compilation reports every incompatible historical run and exits non-zero if any selected video fails. The web process serves cached or locally renderable videos only: when a build would first have to run a simulator-side controller replay, the video route answers 503 with the exact batch command and the run page shows the same hint instead of an empty player. Both rekey the cache when source-image or trace hashes change. A failed encode retains the already-simulated derived replay cache so a retry does not repeat the worker; the bulky replay frames are deleted only after the MP4 and its manifest are durably in place.

Experiments need no Viewer registration: the registry groups runs by the experiment field of their RunPlan. Once a run is indexed and emits the shared observation/action/receipt evidence, it appears under that experiment filter and uses the same Episode Notebook.

LIBERO task cohorts likewise require no curated registry. The Viewer derives their identity from each exact RunPlan's backend, suite and integer task ID; legacy runs may recover the same identity from an exact <suite>-tNN task field. Task links on the main registry open the cross-experiment cohort. This groups trajectories for review but does not claim matched conditions: source, model, prompt, tools, context, budgets and infrastructure validity remain visible per row and must be inspected before comparison.

The cohort telemetry ledger reads each run's existing runtime-metrics.json; it never reparses provider traffic or estimates missing values. “Request context” is provider-reported input tokens per exchange, not cumulative episode workload. “Images per request” counts submitted image instances, so an image retained across multiple requests is counted each time and managed transports may expose a different attachment inventory. “Cache read” is the provider-reported token-weighted ratio; the separate call-hit percentage is not interchangeable with it. Neither measure establishes context relevance, attention quality or behavioral competence. Cross-provider rows remain useful for discovering scale differences, but matched-treatment conclusions require compatible measurement labels and exact Composition inspection.

The cost ledger applies the checked-in viewer/provider-pricing.json snapshot to those direct counters. For Kimi K3, cached input, uncached input and output are priced independently; reasoning output is already a subset of output and is not charged twice. Context Compactor usage is a separate provider workload and is added exactly once. Completed historical runs without a persisted Runtime report may use their final Native AgentSession counters as an explicit fallback; a running session is labelled provisional. The estimate excludes tax, subscriptions, account discounts, simulator/GPU time, SAM service cost and other infrastructure. Updating a provider price adds a new dated catalog entry rather than rewriting the meaning of previously displayed calculations.

Configuration inspection follows the same no-second-registry rule: the run composition page reads the exact resolved RunPlan, context manifest, compiled policy and ToolSurface snapshot, and the Viewer does not silently fill missing or managed provider text.

Interface principles

The Viewer is an evidence instrument, not a presentation site:

  • make the episode's current observations, recorded model responses, actions and measured outcomes readable as one chronological narrative without opening raw JSON;
  • make every original event recoverable by stream and line, with exact payload and hashes visible beside—not replaced by—derived observation context;
  • let the stable outline, large images and restrained progressive disclosure reduce navigation cost on long multimodal trajectories;
  • keep trajectory controls keyboard accessible and visually distinct from task-catalog and raw-event pages;
  • keep provenance available but collapsed by default;
  • prefer short labels and exact values over explanatory UI copy;
  • do not animate or decorate evidence in ways that imply motion, contact or success not present in the recorded artifacts.

The visual language is an editorial lab notebook rather than a live chat console: warm evidence surfaces, a dark overview reel, serif episode headings, monospace identities, and restrained semantic orange/blue/red/green. The chronology and execution hierarchy borrow from reviewed CapX and Agent-as-Policy viewer patterns, but color is never a substitute for the recorded verdict, visibility label or receipt.

LIBERO / LIBERO-Pro catalog contract

viewer/libero_pro_catalog.py preserves the task-order and perturbation model first presented in the historical Agent-as-Policy Atlas at commit a762defefdecff6286ba3079cb02a77cd5327141, but rebuilds the content against the current ORA source pins: LIBERO-Pro code 2b910b5b5f53016bef9907632f6f840f1ce2229c and dataset c86fc3b8293185a6f373677018ff3e37f8391602. The tracked snapshot contains all 130 original tasks: 30 controlled-transfer tasks in Spatial/Object/Goal and the LIBERO-100 collection composed of 90 short-horizon pretraining tasks plus 10 relatively long-horizon downstream tasks. Task IDs are suite-local and preserve the benchmark's declared order; they are never inferred from lexical filename order.

Exactly 40 tasks—Spatial, Object, Goal and LIBERO-Long—are source-paired LIBERO-Pro anchors. Each anchor projects four exact, Runtime-registered variants—position (swap), language (lan), object appearance (object) and task logic (task)—for 16 suites and 160 configurations. The selected-task panel displays the exact BDDL instruction for every variant. A task perturbation can change the instruction, target object and goal, so equal task IDs across variants are alignment slots rather than proof of identical semantics.

The same pinned dataset contains a separate seven-case robustness extension: lighting/noise, camera angle, runtime object movement, texture, occlusion, shape, and initial position/yaw. The Viewer catalogs 40 BDDL assets per case (280 total) and links their source identities. The experiment registers one suite handle per base family and case (28 handles), while task id selects one of the 280 exact cells. Admission binds the matching parser/application source, strict config hash, base-suite init state and unchanged official predicate; adding a card or BDDL link alone still cannot expand the Environment registry.

Every core task has 50 pinned initialization states. The Viewer explains the Runtime mapping (seed mod 50) without exposing initial-state tensors or simulator ground truth to a policy. The catalog contains no demonstration, policy rollout, success verdict, or per-task Pro video; locally recorded episodes remain available only through the exact suite/task run-registry link.

Seed-0 preview cache

The task index uses 130 original LIBERO seed-0 images. The 40 Pro-anchor task plates, four-way comparisons and robustness cards additionally use 160 core plus 280 robustness images, for 570 specimens total. LIBERO-90 never receives fabricated Pro variants. Every image is rendered from the pinned task BDDL and the first pinned init state with agentview at 256×256 before any action. They are useful scene specimens, but remain explicitly separate from demonstrations, policy-visible observations, episode runs, evaluation and sealed evidence.

Preview generation is an explicit offline operation. The Viewer-side compiler contains only the catalog, source identities, cache plan and manifest logic; it launches environment/backends/libero_pro/preview.py in the pinned external interpreter for all MuJoCo work. Export LIBERO_PRO_PYTHON, LIBERO_PRO_ROOT and LIBERO_PRO_DATA_ROOT, then run:

uv run --locked ora-viewer compile previews
uv run --locked ora-viewer compile previews --status

The compiler verifies clean exact code/data revisions, exact BDDL languages, source hashes, image dimensions and the 130/160/280 split before atomically publishing outputs/viewer-derived/libero-pro-previews/manifest.json. Four workers are used by default; --jobs is bounded to 1–8. Current-identity PNGs are reused and all generated files remain ignored.

The field-guide routes and query projection live in viewer/libero_pro_gallery.py; its HTML lives in viewer/templates/libero_pro_gallery.html. The main Viewer application only registers that presentation blueprint and supplies the run-registry and preview manifest callbacks. Neither module imports the process-isolated simulator backend.

Robustness previews use the same strict parser and static application boundary as a live episode. They show the post-init, pre-action scene. Consequently the runtime-object-move preview intentionally precedes its near-grasp/step-160 event; the dynamic event itself is qualified and recorded during execution, not fabricated in the Gallery.

RoboTwin catalog contract

viewer/robotwin_catalog.py is a presentation snapshot migrated from the historical Agent-as-Policy Atlas at commit a762defefdecff6286ba3079cb02a77cd5327141. It contains exactly 50 unique task identifiers, seven presentation families, five embodiment columns, generator acceptance percentages, average expert steps, object labels, source links and the official world/head MP4 mapping.

Environment source links are pinned to RoboTwin revision c3ddfa8b97d5519efa828b075999bd0006778e5e. Documentation pages and MP4 files remain externally hosted by RoboTwin; the catalog records their mapping but does not vendor or seal those resources. A missing external video therefore does not invalidate a Robot Harness run.

The catalog is deliberately viewer-owned. It is not a task registry and does not authorize experiments on all 50 tasks; task, seed, budget and qualification choices belong to the RunSpec.

Provenance and privilege boundary

RoboTwin gallery videos are produced by task-specific play_once() programs. Those programs may read simulator actor poses and functional annotations, plan with CuRobo, and retain episodes accepted by planner and task predicates. The videos are useful for understanding task semantics, morphology, and camera coverage, but they are not:

  • Robot Harness policy rollouts;
  • observations or demonstrations exposed to the policy;
  • evidence of Harness success;
  • unique or optimal solutions;
  • substitutes for sealed run artifacts or official evaluation.

The Viewer never changes the policy privilege boundary. Policy-visible inputs continue to come only from privilege-clean observations and the configured context projection.

The run page labels policy-visible observer_camera evidence separately from a recorded native/operator-world.mp4. Current RoboTwin video may instead contain all five synchronized camera panels, but it retains the same Control-only boundary. The page also renders Context, Coding and Camera-disclosure lanes from context-audit.json; operator media is never passed to the policy merely because the Viewer can display it.

Maintenance

  • Keep the original LIBERO catalog at exactly 130 tasks and preserve its 30-task controlled-transfer / 90+10 LIBERO-100 hierarchy. Keep the LIBERO-Pro overlay at exactly 40 anchors, 160 registered core configurations and 280 registered robustness configurations until a new code/data revision and Runtime admission are reviewed together.
  • Keep the seed-0 preview manifest at exactly 130 original plus 160 core plus 280 robustness images; image generation stays outside the web process and generated PNGs never become tracked or sealed evidence.
  • Preserve benchmark-declared task order and exact BDDL languages; do not sort filenames to manufacture task IDs or imply that task perturbations keep one goal fixed.
  • Keep the catalog at exactly 50 unique tasks until adopting a new, explicitly reviewed RoboTwin catalog revision.
  • Update catalog metadata, revision identifiers, tests and this README together.
  • Do not present upstream generator acceptance as policy success.
  • Keep every route read-only and retain path-containment checks for run artifacts.
  • Never present Viewer controller replay as original execution. Bind replay to the exact source, task, seed and recorded controller-command hashes, write it only under viewer-derived/, and label nondeterminism and verdict limits.
  • Never re-run a high-level planner just to make a video. Replay the controller commands that the live backend actually issued; otherwise retain the action-boundary fallback.

The protected contracts are listed in the test inventory. The ora commands are in the command reference; the remaining wrappers are in the script inventory.

Controller replay readers accept historical inline manifest v1 and the current v2 bounded manifest plus hash-bound append-only event journal. The canonical loader reconstructs only committed events and validates command artifacts; Viewer media checks do not treat a v2 header with no inline entries as an empty trace. Journal/reader identity participates in cache validation. The recording optimization does not skip replayed physics, change sampling or claim faster full video rendering.

Default process clips obey the original-only execution source contract. If a captured native control action has no exact policy action-ID join, process metadata lists it in unplaced_execution_chapters and reports captured_control_actions_without_policy_join; the complete execution video still contains those original frames. No policy receipt is invented for it.
