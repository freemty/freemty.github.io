Repository structure

This page describes how the repository is laid out, the import rules that keep it that way, the files that may not move, and the decisions behind the layout. It records the tree as built by the October 2026 restructure; file counts are tracked files, and for Python directories the number of .py modules. tests/repository/test_structure.py checks the import rules, the test tree and the package READMEs on every change, statically, without importing ora.

0. Finding your way in

README.md                what ORA is, and one `ora run` episode
docs/quickstart.md       install, one Synthetic episode, one simulator episode
docs/how-ora-works.md    where the policy, the tools, the environment and the evidence sit in one run
docs/architecture.md     the four layers and the two places a backend lives
docs/code-map.md         one row per package, with a link to its README
<package>/README.md      responsibility; what belongs here and what does not;
                         dependency direction; entry points; documentation

After these six steps a reader can answer three questions. What is shared by every environment: ora/contracts, ora/agent, and the orchestrator and environment cores. What belongs to one simulator: only ora/environment/backends/<sim>/ (the worker half, in the simulator's own interpreter) and ora/orchestrator/backends/<kind>/ (the host half). Where a tool's code is: ora/agent/toolkit/tools/<name>/, one directory per tool.

A new collaborator's first hour (install, the checks, one episode with and without a simulator, the three rules no change may break) is Start contributing; Contributing is the path to a pull request, which .github/pull_request_template.md turns into a checklist.

2. Layers and import rules

ora/app            the `ora` command: parse, ask, print, draw
   |
ora/orchestrator   RunSpec to RunPlan, preflight, leases, launch, the Supervisor's
   |               episode loop, evaluation, sealing, reports;
   |               backends/<kind>/ behind a string registry
   +---------------------------+
   |                           |
ora/agent                   ora/environment
the policy side             sessions, worker, Synthetic;
                            backends/<sim>/ only in the isolated interpreter
   |                           |
   +---------------------------+
   |
ora/contracts      the action envelope and the contracts both sides share

beside the layers: ora/policy (data, pinned by policy.lock), ora/robot_client
(standard library only), ora/version.py, ora/cell (the real-cell kit)
Rule Statement Status
L1 Layers import downward only: app > orchestrator > {agent, environment} > contracts; agent and environment import nothing of each other; policy and version import no ora package; robot_client imports none and only orchestrator and app may import it; cell imports none (it reaches a robot's cell_adapter by a module-name string) and only environment, orchestrator and app may import it Holds
L2 ora never imports viewer (the live world view moved into ora/orchestrator/world_view.py; viewer imports ora) Holds
L3 The orchestrator core reaches a backend only through ora/orchestrator/backends/registry.py, whose BACKENDS maps runtime.kind to "ora.orchestrator.backends.<kind>.backend:BACKEND"; the seven pinned ora/orchestrator/robodojo_*.py modules count as part of the RoboDojo backend Holds
L4 The environment core imports ora/environment/backends/ only from the isolated-interpreter entry points ora/environment/worker.py and replay_worker.py; nothing outside ora/environment/planners/ imports it (a planner worker is started by module name) and a planner imports no backend Holds
L5 ora/agent never imports ora/environment/backends, ora/orchestrator or ora/app Holds
L6 Inside ora/agent, a unit imports only lower units: pi, tui > session_core, scripted > context > {memory, code_mode} > toolkit/host > {composition, toolkit} > providers, model_services > evidence, sessions > contracts, error_classes; the toolkit's host, which holds the tool runtime frame (host/runtime/), counts as a unit of its own, so nothing else in toolkit imports it Holds
L7 Retired with the ora/agent/tools package (P21): it ordered that package's family sub-packages, and the tool runtime frame they held now sits in ora/agent/toolkit/host/runtime/ Retired
L8 Tests import only ora, viewer, examples and tests.support; no test module imports another Holds
L9 A package with sub-packages imports nothing eagerly in its __init__.py (lazy facades); allowed exceptions: ora/agent/__init__.py re-exports its contracts, and ora/environment/backends/robodojo/__init__.py imports session.py because it is a pinned kernel file Holds

An OrchestratorBackend has 24 fields besides its kind: only resolve_runtime and preflight_runtime are required, capabilities is data, and every other hook is optional with a core default. Each backend package's __init__.py holds a docstring only, and registry.backends() is the one call that imports all of them. The core sub-packages are not layered among themselves yet: episode and evaluation read each other's vocabularies, and spec and preflight read episode/agent_core.py.

Help has three levels: ora --help (the groups, in English or Chinese), ora <command> --help (argparse), and ora help <topic> (the pages in ora/app/help/, package data). A topic wins over a command of the same name: ora help play prints the page, ora play --help the options. docs/usage/cli-reference.md is generated from the parser by ora dev cli-reference --write, and tests/ora/app/test_cli_reference.py fails on a stale page; docs/usage/commands.md is the hand-written guide.

Operator tools a backend owns are reached by kind, not imported by the app: ora spec ENV TOOL, ora qualify ENV TOOL and ora play audit --env ENV run the tools the backend declares (spec_tools, qualify_tools, play_audit). ora spec libero covers LIBERO-Pro; the RoboTwin seed-scan tool is ora qualify robotwin qualify. The Viewer's offline builds are ora-viewer compile previews|videos.

Twenty-five modules keep a python -m entry point or run by path because a process starts them (the simulator worker, the supervisor, probes, audits, installers, the robot client); ora/app/README.md lists them with who starts each, and tests/ora/app/test_main.py checks the list against the __main__ guards. Folded tools left no compatibility shim at their old python -m path.

scripts/ keeps ora, ora-remote, docs, setup-robodojo (the pinned RoboDojo installer's receipt names it), lib/python.sh and dev/{check, compare-model-visible, refresh-vendored-pins}; the other wrappers became ora or ora-viewer commands.

8. tests/

The test tree mirrors the code tree: tests/ora/<package path>/test_*.py covers ora/<package path>/, and tests/viewer/ covers viewer/. Only tests/support/ may be imported across directories (rule L8); fixed samples live in tests/data/. tests/agent_core/ holds the TypeScript-core parity and sealed-replay tests, selected by the agent_core marker, and tests/repository/ the repository-wide guards (canonical imports, module size ratchet, packaging, policy lock, this structure). Lanes are selected by marker, not by path. tests/README.md maps each directory to the code it covers, and Testing says which check to run for a change.

13. The interface for training loops

ORA has no Python training code; a training loop needs three things, and each exists:

  1. A replaceable model endpoint. The policy is reached through a provider profile (ora/agent/providers/, ora providers add): a checkpoint being trained is one more OpenAI-compatible or Anthropic Messages endpoint.
  2. Identifiable calls. Each episode's agent trace (agent-events.jsonl) records every model call with run_id, policy_session_id, observation_step and model_call_id, and the exact request bytes by sha256. These ids are not on the wire: only a profile that declares session_affinity: x_session_id_run_v1 sends X-Session-ID: ora:<run_id>:native, so a server can group requests by run.
  3. Evidence export. The reward is the run's official_success; ora trace-validate RUN checks the trace and ora export-sft RUN writes the accepted model calls as tool-call JSONL with their attribution, loss mask, provider usage and manifest (evidence/trace_verify.py, evidence/sft_export.py); --view wire exports every call as it was sent, each image once, with each call's token ids, and proves the export rebuilds the archived requests (evidence/wire_export.py, evidence/token_ids.py); --view openai packages it for sharing with a standard-library verify tool (evidence/openai_package.py, evidence/openai_package_tool.py). Concurrency comes from the resource leases and the suite queue.

Connect a training loop and ora help rl-interface describe it for users.

As built, a few choices differ from the first plan:

  • Backend registry entries name a module per package (ora.orchestrator.backends.robodojo.backend:BACKEND), so each package's __init__.py stays empty (rule L9).
  • The shared vocabularies went where rule L6 allows: tool names to composition/surface/tool_names.py, units to composition/surface/units.py, context slots to composition/prompt/slots.py, the SAM3 and Contact-GraspNet clients to model_services/clients.py.

  • evidence/trajectory.py, memory/artifacts.py and providers/__init__.py stay as re-exporting facades for the orchestrator's imports.
  • scripts/setup-robodojo stays (the pinned installer names it); the RoboTwin seed-scan subcommand is still qualify, not scan.
  • ora/environment/backends/robolab/ has no __init__.py yet.
