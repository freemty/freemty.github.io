ora doctor

usage: ora doctor [-h] [--env {synthetic,robotwin,libero_pro,robodojo,local}] [--root ROOT] [--json]

    ora doctor [--env synthetic|robotwin|libero_pro|robodojo] [--json]

`ora replay`: a finished run in the browser, replayed from its evidence, or made into a video.

    ora replay RUN [--speed 16] [--motion-speed 1|same] [--from S] [--port N] [--no-browser]
                   [--view compact|detailed] [--expand-thinking] [--lang en|zh] [--publish]
    ora replay RUN --program DIR | --check OUT [--resource-profile P]
    ora replay RUN --scene [--scene-traces DIR] [--resource-profile P]
    ora replay RUN --incident N --report OUT [--stack-run RUN] [--branch both|recorded|current] [--preview]
                   [--resource-profile P]
    ora replay RUN --export OUT.mp4 [--speed 16] [--motion-speed 1|same] [--fps 30] [--size 1920x1080] [--scale 2] [--zoom 1]
                   [--from S] [--to S] [--workers N] [--publish] [--ffmpeg PATH] [--chromium PATH]
                   [--export-python PY]

The page is `ora web`'s own (ora-pi/web), shown at a clock over the run's recorded
time: its web server rebuilds what the live page showed from the run's evidence
(Pi's session, the Supervisor's events, the execution capture and the operator
views: ora-pi/web/server/replay.ts) and attaches to nothing. The gateway in front
is `ora web`'s (launch token, cookie, loopback Host), passing the page and its one
route, GET /api/replay. Nothing in the run is written, and a live run is refused
(`ora web` shows it).

The replay has two rates: the waiting and thinking between the robot's actions play at
`--speed` (16x by default), and each action, from its start to its end with any settling
frames, plays its execution capture by the frames' simulated time at `--motion-speed` (1x by
default: real simulated time, never shorter than the action at `--speed`). Only captured frames
are shown, each held until the next; nothing is interpolated. `--motion-speed same` keeps one
speed throughout. The page has the same switches. `--export` draws the replay into a video at
those rates: a headless Chromium opens the page, the page's playback is set to each frame's
moment in turn (a virtual clock, so the video keeps the replay's rates whatever the machine's
speed and is the same every time), each frame is a screenshot drawn at `--scale` device pixels
per CSS pixel and scaled down to `--size`, and ffmpeg encodes H.264 (yuv420p, CRF 16). A corner
of the page says what plays and how fast ("robot motion · real time", "thinking · 16×"); the
report beside the video lists every stretch with its rate and times. `--publish` leaves the
run's ID and absolute paths out of the page.

`--program` and `--check` work on the run's replay program: its agent actions as code
that reproduces the run (`environment/replay_program.py`). Every run sealed with this
version carries it in `replay-program/`; `--program DIR` writes it for any run, outside
the run. `--check OUT` re-executes it on the run's simulator (the plan's interpreter,
the caller's CUDA_VISIBLE_DEVICES first), compares every action's end pose with its
receipt bit for bit and the official verdict with the run's, and writes
OUT/replay-program-check.json. A RoboCasa365 check also compares the base's end pose and a
hash of the whole scene at every action. A RoboDojo check runs the qualification control
replay on `--resource-profile` and needs the run's host marker. A RoboLab check runs in the
environment worker a run uses, on one card. A run that records no per-tick controls (a
RoboCasa365 or RoboLab run sealed before they were recorded) has no program, so `--check`
refuses it and `--program DIR` writes DIR/unavailable.json.

`--scene` runs the same check on a RoboTwin, LIBERO-Pro, RoboCasa365, RoboDojo or RoboLab run and, when it passes,
keeps the scene of that re-execution for the run dashboard's 3D replay: every body's world pose (about 50 Hz on
RoboTwin and LIBERO-Pro, every fifth SAPIEN step and every tenth MuJoCo step, every native action on
RoboDojo, 25 Hz, RoboCasa365, 20 Hz, and RoboLab, 15 Hz, plus each action's last step) and each body's visual mesh,
in `scene-trace/<run_id>/` beside the run's `runs/` directory or under `--scene-traces DIR` (`environment/scene_trace.py`). A
RoboDojo run needs `--resource-profile`, as its `--check` does. The run itself is not written. A run
whose re-execution diverges gets no trace; the report beside the traces says why. A re-execution that matches
the run bit for bit keeps its trace even if its verdict reads differently: the result and the report say
`verdict_differs`. Scene poses are
private simulator state: the trace is for a developer and reaches no policy.

`--incident N` replays the run up to action N and runs N again with no model, to see what
this checkout does with a move that once went wrong (`orchestrator/evaluation/incident_replay.py`).
On RoboTwin and LIBERO-Pro the `recorded` branch runs the recorded controls and the `current`
branch submits the recorded target to the motion stack of `--stack-run`, a run sealed on this
checkout such as a merge smoke; `--stack-run` must share the source run's simulator revisions.
On RoboDojo `--resource-profile` names a slot on the run's host and the run must be a toolkit
run: only `current` runs, through `ora toolkit replay --live --execute-action`, on the default
baseline's tool surface, planner and timing, and it needs a clean checkout.
OUT/incident-replay.json says whether the prefix matched bit for bit, each branch's receipt or
refusal, the stack it ran on, and which bodies moved. Scene poses are private simulator state:
the report is for a developer and reaches no policy.

The export needs Playwright for Python with its Chromium (`pip install
playwright==1.56.0 && playwright install chromium`, or `uv` on PATH, which runs it
as `uv run --no-project --with playwright==1.56.0`) and ffmpeg (on PATH,
ORA_FFMPEG or --ffmpeg). Neither is a dependency of ORA.

positional arguments:
  run                   the finished run's ID or directory

options:
  -h, --help            show this help message and exit
  --speed SPEED         the speed of the waiting and thinking between the robot's actions (default
                        16)
  --motion-speed X|same
                        the speed of each action's motion against its simulated time (default 1:
                        real time); `same`: --speed throughout
  --view {compact,detailed}
                        how the conversation is drawn (default compact)
  --expand-thinking     every thought open
  --lang {en,zh}        the page's language (default: the browser's)
  --publish             leave the run's ID and absolute paths out of the page
  --from S              start S seconds into the run's recorded time

the page:
  --port PORT           loopback port (default: a free one)
  --no-browser          print the link instead of opening it

a video (--export):
  --export OUT.mp4      draw the replay into this H.264 video and exit
  --fps FPS             frames per second (default 30)
  --size SIZE           the video's WIDTHxHEIGHT (default 1920x1080)
  --scale SCALE         device pixels per CSS pixel the page is drawn at before scaling to --size
                        (default 2)
  --zoom ZOOM           the page's zoom: its layout is --size / zoom CSS pixels (default 1)
  --to S                end S seconds into the run's recorded time (default: its end)
  --workers WORKERS     pages drawing frames side by side (default 4)
  --crf CRF             H.264 quality, lower is better (default 16)
  --ffmpeg FFMPEG       ffmpeg to encode with (default: ORA_FFMPEG, then PATH)
  --chromium CHROMIUM   Chromium to draw with (default: Playwright's)
  --export-python EXPORT_PYTHON
                        a Python with Playwright (default: this one, else uv)

the replay program (--program, --check):
  --program DIR         write the run's replay program (program.json, program.py) to DIR outside the
                        run and exit; a sealed run already carries it in replay-program/
  --check OUT           re-execute the replay program on the run's simulator, check every action's
                        end pose against its receipt bit for bit and the verdict, write OUT/replay-
                        program-check.json
  --resource-profile RESOURCE_PROFILE
                        RoboDojo --check, --scene or --incident: the qualified slot to replay on

the scene trace (--scene):
  --scene               re-execute the run as --check does on RoboTwin, LIBERO-Pro, RoboCasa365,
                        RoboDojo or RoboLab and, if it passes, write its scene trace for the run

  --scene-traces DIR    --scene: write DIR/<run_id>/ (default: scene-trace/<run_id>/ beside the
                        run's runs/)

one bad action (--incident):
  --incident N          replay the run up to action N, then run N again on this checkout's motion
                        stack; needs --report, and --stack-run or --resource-profile
  --report OUT          --incident: an empty directory for the report
  --stack-run RUN       --incident on RoboTwin or LIBERO-Pro: a run sealed on this checkout, whose
                        motion stack the action runs on
  --branch {both,recorded,current}
                        --incident: which branches to run (default both)
  --preview             --incident on RoboDojo: what a dry run of the action shows at that state,
                        written to OUT/preview.png, instead of running it

ora web

usage: ora web [-h] [--last] [--port PORT] [--socket SOCKET] [--token-file TOKEN_FILE]
               [--no-browser]
               [run]

`ora web`: a live run in the browser, ORA's own page over the run's Pi RPC.

    ora web setup                       install and build the page (ora-pi/web: npm ci, then vite build)
    ora web [RUN] [--last] [--port N | --socket PATH] [--token-file PATH] [--no-browser]

The run's agent core serves Pi's RPC protocol (ora-pi/src/rpc/host.ts). ORA's
web server (ora-pi/web/server, Node; its page seeded from Watercol/pi-web-ui,
MIT) attaches to it through `ora-rpc-attach` as one controlling client and
serves the page: the conversation, the robot's cameras and each step's images
on one screen. In front of it the gateway (web_gateway.py) adds a one-time
launch token exchanged for a cookie, loopback Host and same-origin checks, the
routes the page uses and nothing else, the run's stored images and its world
view (world_view.py), and on a real robot cell the cell's controls
(web_cell.py).

The page is built once by `ora web setup`; the build records a digest of the
sources it was built from (dist/ora-build.json), and `ora web` refuses a page

usage: ora cell [-h] ACTION ...

``ora cell``: set up, watch and recover a real robot cell (``ora/cell``, docs/usage/real-cells.md).

    ora cell init [--example PATH]          validate the cell config against its robot, list devices
    ora cell check                          buses, other controllers, cameras and their depth
    ora cell read | record-rest             the arms, read without enabling anything
    ora cell grippers [--orient]            each gripper opens and closes once to find its limits;
                                            then (or with --orient alone, nothing moving) you say which way each is
    ora cell calibrate --method arm-poses|board-poses|board-relative|charuco|wrists [--square-mm N] [--pattern CxR] [--role R]
    ora cell calibrate --method hand-eye [--square-mm N] [--pattern CxR] [--placements N] [--arms A,B]
                       [--records DIR ...] [--ask terminal|broker]
    ora cell setup [--status] [--redo STEP ...] [--only STEP ...]
                                            a new cell, step by step: devices, rest, grippers, fixed cameras,
                                            hand-eye calibration, table, verify (what is not done yet)
    ora cell board [--port 8765]            the operator's page: state, live cloud, verbs
    ora cell depth-service [...]            the depth completion service (ora.cell.depth.service)
    ora cell home | hold | float | release | estop | diagnose | stop | kill | cameras | can
    ora cell pending | approve [--id ID] [--value V] | decline [--id ID] [--reason TEXT]
    ora cell auto-approve [on|off|status]   motions of the running play worker answer themselves
    ora cell mode [ask|safe|auto|status]    the permission mode: every motion asked, small ones not, or none
    ora cell stop-motion                    the running motion ends where the arms are; they stay held there
    ora cell sim init PATH | status | place X Y [--yaw DEG] | clear | operator [--seconds S]
                                            a simulated cell (``robot.sim``): write one, compare its
                                            calibration with the injected truth, move its board, answer
                                            its questions as the person at the cell would

Every command reads the cell config (``--cell``, else ``$ORA_CELL``, else
``~/.config/ora/cell.yaml``). The operator verbs (home ... can) act at once, also while a
play session moves the arms; ``hold`` and ``float`` keep the arms held and so need a
running cell board, which they reach over HTTP; with a board running every verb goes
through it. ``--json`` prints ``{"ok": true, "result": ...}`` or ``{"ok": false,
"error": ...}`` (exit 1); ``--yes`` skips the confirmation of verbs that make arms limp
or move them by hand.

``calibrate --method hand-eye`` is the guided calibration of a new cell
(``ora/cell/operator/handeye.py``): the person places a checkerboard a few times, the arms
look at it, and one fit measures the fixed cameras, the wrist cameras' mounts, the arms'
bases and their joint zeros; it asks every step (place the board, each motion, the
measured square, writing the result) on this terminal, or through the approval broker
when it has none (``--ask broker``) and prints its progress on stderr (JSON lines with
``--json``). ``--records`` fits earlier captures again without moving anything.

``pending``, ``approve`` and ``decline`` answer the questions a robot's worker asks the
operator (enable the arms, run a motion, release arms that could not get home): they
read and write only the cell's approval files (``$ORA_CELL_APPROVALS``, else beside the
cell lock), never the lock or the hardware. An answer names the question's ``--id``
(``pending`` lists them); without one, on a terminal, the one waiting question is shown
and answered after a yes.

``auto-approve on`` (the operator's "YOLO" switch) makes the play worker that drives the
arms now (``rig_mode on``) answer its own motion questions; enabling the arms and releasing
them are still asked. ``off`` turns it off; ``status`` (the default) says whether it is on.
It too touches only the approval files: the switch lives for that worker only, and a new
worker clears it unless its run was started with ``ora play ... --auto-approve``.

A simulated cell (``robot.sim: true``, docs/usage/real-cells.md) runs every command above
with no hardware: the robot's simulated adapter renders its cameras and moves kinematic
arms. Its lock, approvals and alerts live in its state directory unless
``ORA_CELL_LOCK``, ``ORA_CELL_APPROVALS`` or ``ORA_CELL_ALERTS`` name others, so it never
shares them with a real cell. ``ora cell sim init PATH`` writes such a config;
``sim status`` compares the calibration with the errors the simulation injected (its
``world.json``), ``sim place`` and ``sim clear`` move the checkerboard, and ``sim operator``
is the person at the cell: it answers the broker's questions (board placements, motions,
square size, which way a gripper opens, writing) until stopped.
